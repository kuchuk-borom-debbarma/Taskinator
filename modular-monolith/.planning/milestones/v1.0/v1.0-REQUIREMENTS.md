# Requirements Archive: v1.0 - CWB Automation

## 1. Functional Requirements

### 1.1 Database Schema (`behavior_rule`)
- [x] Create `behavior_rule` table to store automation logic.
- [x] Fields: `id`, `fk_project_id`, `name`, `is_active`, `behavior_type`, `fk_task_id`, `criteria_field`, `criteria_operator`, `criteria_value`, `action_message`, `action_value`, `version`, `created_at`, `updated_at`.
- [x] Support behaviors: `BLOCKER_RESOLUTION`, `PARENT_DELETE_GUARD`, `PRIORITY_CASCADE`, `TEAM_CASCADE`, `BLOCKER_SAFETY_GUARD`, `MEMBER_ASSIGNMENT_GUARD`, `CASCADE_DELETE`, `AUTO_NOTIFY`.
- **Outcome:** Validated.

### 1.2 Pre-Action Guards
- [x] Hook into `TaskService.deleteTask` and `TaskService.updateTask`.
- [x] Synchronous check before DB commit.
- [x] Throw validation error if guard condition fails.
- [x] Specific guards:
    - [x] `PARENT_DELETE_GUARD`: Block if active subtasks exist.
    - [x] `BLOCKER_SAFETY_GUARD`: Block `IN_PROGRESS` if blockers are not complete.
    - [x] `MEMBER_ASSIGNMENT_GUARD`: Block member assignment if team is null.
- **Outcome:** Validated.

### 1.3 Post-Action Cascades
- [x] Kafka-driven background execution.
- [x] Listen for `TASK.CREATED` and `TASK.UPDATED`.
- [x] Evaluate criteria using flat field comparison.
- [x] Execute updates via `taskService.updateTask`.
- [x] Specific cascades:
    - [x] `BLOCKER_RESOLUTION`: Transition parent to READY when subtasks COMPLETE.
    - [x] `PRIORITY_CASCADE`: Propagate priority to subtasks.
    - [x] `TEAM_CASCADE`: Propagate team to subtasks.
    - [x] `CASCADE_DELETE`: Delete subtasks on parent deletion.
    - [ ] `AUTO_NOTIFY`: Send alerts on dependency resolution.
- **Outcome:** Adjusted. `AUTO_NOTIFY` type is defined but execution deferred to future milestone.

### 1.4 System Cleanup
- [x] Remove legacy AST-based engines and suspension logic.
- [x] Wipe existing `auto_action` data.
- **Outcome:** Validated.

## 2. Non-Functional Requirements
- [x] **Performance:** Direct DB queries for relationship traversals (no recursive app-side logic).
- [x] **Reliability:** "Log and Proceed" for cascades; synchronous rollback for guards.
- [x] **Simplicity:** KISS principle; flat targeting only.
- **Outcome:** Validated.

## 3. Testing Requirements
- [x] **E2E Heavy:** Verify guards block transactions and cascades execute via Kafka.
- [x] **Validation:** Ensure legacy code removal doesn't break existing task operations.
- **Outcome:** Validated.
