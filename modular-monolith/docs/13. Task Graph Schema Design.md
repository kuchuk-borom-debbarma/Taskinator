# Task Graph Schema Design

## Goal

Task system use pure graph model. No parent-child. No tree assumptions. Every task stand alone node. Links connect nodes with user-defined labels. UI build focused task + incoming/outgoing network from graph paths.

## Core Rules

1. `project_task` store task node only.
2. `task_link` store direct directed edge.
3. `task_link_materialized` store transitive directed paths.
4. Link labels user-defined text. No fixed enum.
5. Frontend hash label -> stable color.
6. Multiple links with same label allowed.
7. Multiple same-pair links with same label allowed.
8. Path identity use `path_link_ids`, not labels.
9. Incoming paths end at focused task.
10. Outgoing paths start from focused task.

## Why No Parent / Child

Parent-child break mental model for this product. Work is graph, not tree.

Bad:
- force one hierarchy
- hide cross-links
- mix containment with dependency
- confuse UI: "child task" vs "linked task"

Good:
- task = node
- link = directed relationship
- path = graph traversal result

## Tables

### `project_task`

Store node only.

```sql
CREATE TABLE project_task (
    id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    fk_project_id UUID NOT NULL,
    fk_team_id UUID,
    fk_member_id TEXT,
    title TEXT NOT NULL,
    description TEXT NOT NULL DEFAULT '',
    status TEXT NOT NULL DEFAULT 'TODO',
    last_event_id UUID,
    version INTEGER NOT NULL DEFAULT 1,
    created_by TEXT NOT NULL,
    updated_by TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

Purpose:
- task list
- task detail
- assignment
- status/version tracking

Important:
- no `parent_task_id`
- no `materialized_path`

### `task_link`

Store direct edge only.

```sql
CREATE TABLE task_link (
    id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    fk_project_id UUID NOT NULL,
    source_task_id UUID NOT NULL,
    target_task_id UUID NOT NULL,
    label TEXT NOT NULL,
    created_by TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT chk_task_link_not_self CHECK (source_task_id <> target_task_id),
    CONSTRAINT chk_task_link_label_valid CHECK (length(trim(label)) BETWEEN 1 AND 50)
);
```

Meaning:
- `source_task_id` = path start for direct edge
- `target_task_id` = path end for direct edge
- `label` = user text like `blocks`, `relies`, `handoff`, `needs review`

Important:
- no enum
- no uniqueness on `label`
- duplicate labels OK
- duplicate exact edges OK if user creates them

### `task_link_materialized`

Store transitive path rows.

```sql
CREATE TABLE task_link_materialized (
    id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    fk_project_id UUID NOT NULL,
    origin_task_id UUID NOT NULL,
    terminal_task_id UUID NOT NULL,
    path_task_ids UUID[] NOT NULL,
    path_link_ids UUID[] NOT NULL,
    path_link_labels TEXT[] NOT NULL,
    depth INTEGER NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

Meaning:
- `origin_task_id` = full path start
- `terminal_task_id` = full path end
- `path_task_ids` = ordered nodes
- `path_link_ids` = ordered exact direct edges
- `path_link_labels` = ordered display labels
- `depth` = edge count

## Why `path_link_ids` Matter

Labels not enough.

Example:

```text
a -blocks> b
a -blocks> b
```

Two direct edges. Same tasks. Same label. Still two different links.

If materialized row store only:
- `path_task_ids`
- `path_link_labels`

then two paths collapse into one fake path. Wrong.

So exact identity must include `path_link_ids`.

## Path Semantics

For focused task `b`:

Incoming:

```text
a -blocks> b
z -blocks> g -relies> b
```

Rows:

```text
origin=a, terminal=b, path=[a,b]
origin=z, terminal=b, path=[z,g,b]
```

Outgoing:

```text
b -relies> c
b -blocks> x -relies> y
```

Rows:

```text
origin=b, terminal=c, path=[b,c]
origin=b, terminal=y, path=[b,x,y]
```

So one focused task can have many incoming rows and many outgoing rows. Normal. Expected.

## Query Model

### Direct links for task

```sql
SELECT *
FROM task_link
WHERE fk_project_id = $projectId
  AND (source_task_id = $taskId OR target_task_id = $taskId);
```

### Incoming network

```sql
SELECT *
FROM task_link_materialized
WHERE fk_project_id = $projectId
  AND terminal_task_id = $taskId
  AND depth <= $depth
ORDER BY depth ASC, created_at DESC
LIMIT $limit;
```

### Outgoing network

```sql
SELECT *
FROM task_link_materialized
WHERE fk_project_id = $projectId
  AND origin_task_id = $taskId
  AND depth <= $depth
ORDER BY depth ASC, created_at DESC
LIMIT $limit;
```

## GraphQL Shape

Use explicit graph naming. Keep legacy aliases short term if old UI still depends on them.

### Direct edge

```graphql
type TaskLink {
  id: ID!
  sourceTaskId: ID!
  targetTaskId: ID!
  label: String!
  createdBy: String!
  createdAt: String!
}
```

Legacy alias if needed:

```graphql
fromTaskId
toTaskId
type
```

### Materialized path

```graphql
type TaskStory {
  id: ID!
  originTaskId: ID!
  terminalTaskId: ID!
  pathTaskIds: [ID!]!
  pathLinkIds: [ID!]!
  pathLinkLabels: [String!]!
  pathTasks: [Task!]!
  depth: Int!
  createdAt: String!
}
```

Legacy alias if needed:

```graphql
originId
terminalId
pathLinkTypes
```

### Focused network query

```graphql
type TaskNetwork {
  incoming: [TaskStory!]!
  outgoing: [TaskStory!]!
}
```

```graphql
taskNetwork(projectId: ID!, taskId: ID!, depth: Int = 3, limit: Int = 20): TaskNetwork!
```

## Path Build Logic

When direct edge created:

```text
A -> B
```

Materializer must create:
- direct path `A -> B`
- any path ending at `A`, extended to `B`
- any path starting at `B`, extended from `A`
- any full bridge through `A -> B`

Example:

```text
X -> A
A -> B
B -> Y
```

Materialized rows:

```text
A -> B
X -> A -> B
A -> B -> Y
X -> A -> B -> Y
```

## Cycle Prevention

Reject `source -> target` if `target` already reaches `source`.

Check:

```sql
SELECT 1
FROM task_link_materialized
WHERE fk_project_id = $projectId
  AND origin_task_id = $targetTaskId
  AND terminal_task_id = $sourceTaskId
LIMIT 1;
```

Also reject self-link:

```sql
source_task_id <> target_task_id
```

## Index Design

### `project_task`

```sql
CREATE INDEX idx_project_task_project_created
ON project_task(fk_project_id, created_at DESC, id DESC);

CREATE INDEX idx_project_task_team
ON project_task(fk_project_id, fk_team_id)
WHERE fk_team_id IS NOT NULL;

CREATE INDEX idx_project_task_member
ON project_task(fk_project_id, fk_member_id)
WHERE fk_member_id IS NOT NULL;

CREATE INDEX idx_project_task_status
ON project_task(fk_project_id, status);
```

### `task_link`

```sql
CREATE INDEX idx_task_link_source
ON task_link(fk_project_id, source_task_id, created_at DESC);

CREATE INDEX idx_task_link_target
ON task_link(fk_project_id, target_task_id, created_at DESC);

CREATE INDEX idx_task_link_pair
ON task_link(fk_project_id, source_task_id, target_task_id);

CREATE INDEX idx_task_link_label
ON task_link(fk_project_id, lower(trim(label)));
```

### `task_link_materialized`

```sql
CREATE INDEX idx_task_path_origin_depth
ON task_link_materialized(fk_project_id, origin_task_id, depth);

CREATE INDEX idx_task_path_terminal_depth
ON task_link_materialized(fk_project_id, terminal_task_id, depth);

CREATE INDEX idx_task_path_task_ids
ON task_link_materialized USING GIN(path_task_ids);

CREATE INDEX idx_task_path_link_ids
ON task_link_materialized USING GIN(path_link_ids);

CREATE INDEX idx_task_path_link_labels
ON task_link_materialized USING GIN(path_link_labels);
```

Optional exact-path dedupe:

```sql
CREATE UNIQUE INDEX uniq_task_path_exact_links
ON task_link_materialized(fk_project_id, path_link_ids);
```

This still allow duplicate labels. Unique key use exact link ids.

## API / UI Split

Backend job:
- auth
- validate link label
- prevent cycles
- store direct edges
- build materialized paths
- return incoming/outgoing network

Frontend job:
- hash `label` -> stable color
- render path rows
- compact long paths with `...`
- highlight focused task in incoming/outgoing path

Backend must not care about color.

## Why This Design Good

- graph-first, matches product
- no fake hierarchy
- direct edges cheap
- incoming/outgoing queries cheap
- duplicate labels safe
- exact path identity safe
- focused task network easy for UI
- memory-efficient frontend possible

## Non-Goals

Not solving here:
- path ranking heuristic
- semantic label registry
- global label taxonomy
- weighted edges
- cross-project links
- path scoring by freshness / ownership

Can add later without changing base graph model.
