

# 🧠 Task Graph Schema Design (Final)

---

## 🎯 Goal

Build a **graph-based task system** where:

* Every task is an independent node
* Tasks are connected via labeled, directed links
* UI shows a **focused task** with its **incoming and outgoing paths**
* System supports **deep graphs**, but UI loads data **incrementally**

---

## ⚠️ Key Constraint

```text
Unlimited graph depth (for users)
BUT bounded depth per request (for performance)
```

---

# 🧩 Core Model

```text
Task (node)
Link (edge)
Reachability (index)
Path (computed on demand)
```

---

## ✅ Core Rules

1. `project_task` stores nodes only
2. `task_link` stores direct edges only
3. `task_reachability` stores transitive connectivity (NOT paths)
4. Paths are **built at read time** using bounded traversal
5. Labels are user-defined (no enum)
6. Duplicate labels allowed
7. Duplicate edges allowed
8. No parent-child hierarchy
9. Incoming paths end at focused task
10. Outgoing paths start from focused task

---

# 🚫 Why No Materialized Paths

Old approach:

```text
Store full paths in DB
```

Problems:

* 💣 Path explosion (combinatorial growth)
* 💣 Massive storage
* 💣 Expensive updates on every write
* 💣 Hard to maintain consistency

---

# ✅ New Approach

```text
Store connectivity → compute paths on demand
```

## 1. `project_task` (Node)

```sql
CREATE TABLE project_task (
    id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    fk_project_id UUID NOT NULL,
    fk_team_id UUID,
    fk_member_id TEXT,
    title TEXT NOT NULL,
    description TEXT NOT NULL DEFAULT '',
    status TEXT NOT NULL DEFAULT 'TODO',
    last_event_id UUID,
    version INTEGER NOT NULL DEFAULT 1,
    created_by TEXT NOT NULL,
    updated_by TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

---

## 2. `task_link` (Direct Edge)

```sql
CREATE TABLE task_link (
    id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    fk_project_id UUID NOT NULL,
    source_task_id UUID NOT NULL,
    target_task_id UUID NOT NULL,
    label TEXT NOT NULL,
    created_by TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT chk_task_link_not_self CHECK (source_task_id <> target_task_id),
    CONSTRAINT chk_task_link_label_valid CHECK (length(trim(label)) BETWEEN 1 AND 50)
);
```

### Meaning

```text
A -requires-> B
```

* `source_task_id` = A
* `target_task_id` = B
* `label` = "requires"

---

## 3. `task_reachability` (Transitive Index)

```sql
CREATE TABLE task_reachability (
    fk_project_id UUID NOT NULL,

    ancestor_task_id UUID NOT NULL,
    descendant_task_id UUID NOT NULL,

    min_depth INTEGER NOT NULL,
    path_count INTEGER NOT NULL DEFAULT 1,

    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    PRIMARY KEY (fk_project_id, ancestor_task_id, descendant_task_id)
);
```

---

## 🧠 What This Stores

```text
A → D (depth = 3)
```

Means:

```text
A can reach D in 3 steps
```

---

## ❗ What It Does NOT Store

* ❌ full paths
* ❌ labels
* ❌ multiple path combinations

# 🔍 Query Model

---

## 1. Direct Links (for UI edges)

```sql
SELECT *
FROM task_link
WHERE fk_project_id = $projectId
  AND (source_task_id = $taskId OR target_task_id = $taskId);
```

---

## 2. Incoming Nodes (fast filter)

```sql
SELECT ancestor_task_id, min_depth
FROM task_reachability
WHERE fk_project_id = $projectId
  AND descendant_task_id = $taskId
  AND min_depth <= $depth
ORDER BY min_depth ASC
LIMIT $limit;
```

---

## 3. Outgoing Nodes

```sql
SELECT descendant_task_id, min_depth
FROM task_reachability
WHERE fk_project_id = $projectId
  AND ancestor_task_id = $taskId
  AND min_depth <= $depth
ORDER BY min_depth ASC
LIMIT $limit;
```

---

# 🔁 Path Building (Application Layer Traversal)

Instead of using Recursive CTEs, which are hard to cache and optimize at 10k RPS, the system uses a **Neighborhood Fetch + In-Memory Stitching** strategy.

---

## Step 1: Fetch Neighborhood IDs
Get all IDs within the bounded depth using the `task_reachability` index.

```sql
WITH neighborhood_ids AS (
    SELECT ancestor_task_id as id FROM task_reachability 
    WHERE descendant_task_id = $focusedTaskId AND min_depth <= $depth
    UNION
    SELECT descendant_task_id as id FROM task_reachability 
    WHERE ancestor_task_id = $focusedTaskId AND min_depth <= $depth
    UNION
    SELECT $focusedTaskId::uuid
)
SELECT id FROM neighborhood_ids;
```

---

## Step 2: Fetch Flat Links
Fetch the exact "truth" (labels, metadata) for all links connecting those nodes.

```sql
SELECT * FROM task_link
WHERE source_task_id IN (SELECT id FROM neighborhood_ids)
  AND target_task_id IN (SELECT id FROM neighborhood_ids);
```

---

## Step 3: Stitching (TypeScript)
The `TaskService` uses a standard Graph Traversal (e.g., DFS) on the fetched flat links to construct the `TaskStory` paths returned to the UI.

---

## 🧠 Important Constraints

```text
Depth MUST be bounded
Result count MUST be limited
```

# 📑 Pagination Strategies

To maintain high performance and a clean UI, the system employs two distinct pagination models.

---

## 1. Temporal Pagination (The Task Window)
*   **Context**: The flat list of all tasks in the project (Index Panel).
*   **Strategy**: **Cursor-based Pagination** (Ordered by `created_at` + `id`).
*   **Implementation**: Uses `getTasks(after: String)` to fetch the next batch of nodes.
*   **Why**: Optimized for chronological discovery and standard list browsing.

---

## 2. Spatial Pagination (The Connected Network)
*   **Context**: The graph-based "Stories" of a focused task.
*   **Strategy**: **Radial Discovery (Depth-based)**.
*   **Implementation**: 
    1.  Fetch the next 20 IDs from `task_reachability` ordered by `min_depth ASC`.
    2.  Stitch only the paths involving those specific IDs.
*   **Why**: Prioritizes immediate neighbors (Depth 1) and allows users to "expand" the network radially as needed.

# ⚡ Index Design

---

## Reachability

```sql
CREATE INDEX idx_reach_desc
ON task_reachability(fk_project_id, descendant_task_id, min_depth);

CREATE INDEX idx_reach_anc
ON task_reachability(fk_project_id, ancestor_task_id, min_depth);
```

---

## Links

```sql
CREATE INDEX idx_task_link_source
ON task_link(fk_project_id, source_task_id);

CREATE INDEX idx_task_link_target
ON task_link(fk_project_id, target_task_id);

CREATE INDEX idx_task_link_pair
ON task_link(fk_project_id, source_task_id, target_task_id);
```

# 🚀 Why This Design Works

---

## ✅ Scalable

* no path explosion
* no large arrays
* no massive writes

---

## ✅ Fast Reads

* reachability = O(1) filter
* CTE = bounded

---

## ✅ Write-Friendly

* only update reachability
* no full graph recompute

---

## ✅ UI Friendly

* depth-based loading
* incremental rendering
* predictable performance
