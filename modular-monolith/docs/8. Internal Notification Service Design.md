# 8. Internal Notification Service Design

The Internal Notification Service handles the "In-App Inbox" for users. It is designed for high-concurrency (10k RPS) and provides a persistent record of system events relevant to a specific user.

## Data Model

| Field | Type | Description |
| :--- | :--- | :--- |
| `id` | UUID | Primary key. |
| `fk_user_id` | TEXT | The recipient (bucket owner). |
| `title` | TEXT | Short summary. |
| `message` | TEXT | Detailed notification body. |
| `type` | TEXT | Category (e.g., ASSIGNMENT, SYSTEM_GUARD, MENTION). |
| `metadata` | JSONB | Contextual data (ids for navigation). |
| `is_read` | BOOLEAN | Read status. |
| `created_at` | TIMESTAMP | Creation time (Partition Key). |

## Scaling Strategy

1. **Table Partitioning**:
   - The `internal_notification` table is partitioned by `created_at` (RANGE).
   - Old partitions (e.g., > 90 days) can be detached and archived or dropped to maintain performance.

2. **Partial Indexing**:
   - `idx_user_unread` is a partial index (`WHERE is_read = FALSE`).
   - This ensures that fetching the "Unread Count" or "Unread List" for a user's header remains $O(1)$ regardless of how many millions of read notifications exist.

3. **Batched Delivery**:
   - For system-wide events, the service uses `INSERT INTO ... SELECT ...` patterns to notify multiple users in a single database round-trip.

## API Patterns (Future)
- `GET /notifications`: Fetches paginated feed for current user.
- `PATCH /notifications/:id/read`: Marks as read.
- `POST /notifications/read-all`: Bulk mark as read for efficiency.
