# 6. Outbox Pattern with wCTEs (Data-Modifying CTEs)

## Overview
As the Application scaled to our target **10,000 Requests Per Second (RPS)**, we discovered a bottleneck in the traditional microservices message coordination. Services would perform a database commit and then explicitly call `eventBus.publish` to Kafka.

This pattern leads to the **Dual Write Problem**. If a Node.js process crashes between the PostgreSQL commit and the Kafka acknowledgment, the message is permanently lost. 

## The wCTE Solution
Taskinator leverages **Data-Modifying CTEs (wCTEs)** to ensure exactly-once delivery with near-zero latency. PostgreSQL `WITH` clauses allow us to perform `INSERT` statements inside the same atomic transaction as the entity creation, without additional round-trips.

## How It Works
When a domain event occurs, we wrap both the core entity generation and the Outbox persistence together in a single `sql` statement.

### Explicit Topic Pattern
Unlike earlier versions that used "magic" discovery, we now store the **Physical Kafka Topic** explicitly in the outbox table.

```sql
WITH inserted_project AS (
    INSERT INTO project (name, description, fk_user_id)
    VALUES (${data.name}, ${data.description}, ${data.userId})
    RETURNING * 
),
inserted_outbox AS (
    INSERT INTO outbox_events (kafka_topic, kafka_key, payload)
    SELECT 
        'project-events', -- Explicit Physical Topic
        id::text,
        jsonb_build_object(
            'type', 'PROJECT.CREATED', -- Event Type in payload
            'projectId', id,
            'userId', fk_user_id,
            'name', name
        )
    FROM inserted_project
)
SELECT * FROM inserted_project
```

### The Breakdown
1. **Explicit Topic**: The `kafka_topic` column stores the target topic (e.g., `project-events`). This ensures the Relayer doesn't need complex mapping tables.
2. **Type within Payload**: By including the `type` inside the `payload` JSON, we maintain a standard schema that all consumers can parse easily.
3. **Atomic Consistency**: The project and its outbox entry are created in a single database operation.

## The Background Relayer
The `OutboxRelay` is a lightweight process that:
1. Loops every 1,000ms.
2. Sweeps up to 100 entries from `outbox_events`.
3. Pushes the payloads directly to the specified `kafka_topic`.
4. Deletes the outbox entries upon successful Kafka acknowledgment.

This pattern ensures that as long as the database entry exists, the event will eventually be published to Kafka.
