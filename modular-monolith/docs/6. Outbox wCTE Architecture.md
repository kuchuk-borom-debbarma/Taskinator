# 6. Outbox Pattern with wCTEs (Data-Modifying CTEs)

## Overview
As the Application scaled to our target **10,000 Requests Per Second (RPS)**, we discovered a bottleneck in our traditional microservices message coordination pattern. Services would perform a database commit, and then explicitly call `eventBus.publish` to Kafka.

This pattern leads to a known architectural risk known as the **Dual Write Problem**. If a Node.js process crashes in the fraction of a millisecond between the PostgreSQL commit and the Kafka acknowledgment, the message is permanently lost. Standard resolution typically involves manual application-level Two-Phase Commits (2PC) or an Outbox table utilizing heavy, application-managed explicit transactions.

We require exactly-once consistency with minimal network latency and memory overhead.

## The wCTE Solution
Rather than manually creating an `outbox_events` table and opening long-lived active Node.js `BEGIN ... COMMIT` logic, we leveraged an extremely robust PostgreSQL capability: **Data-Modifying CTEs (wCTEs)**.

PostgreSQL `WITH` clauses allow you to perform `INSERT`, `UPDATE`, or `DELETE` statements *inside* the CTE graph before the primary `SELECT` is executed. Because it is a single parsed SQL query, PostgreSQL executes all CTE nodes intrinsically inside an implicit, sub-millisecond atomic transaction without round-trip network lag!

## How It Works
When a domain event occurs (such as Project Creation), we wrap both the core entity generation and the Outbox persistence together in a single `sql` statement via Kysely.

```sql
WITH inserted_project AS (
    INSERT INTO project (name, description, fk_user_id)
    VALUES (${data.name}, ${data.description}, ${data.userId})
    RETURNING * -- Crucial: we return the entity to cascade it downwards!
),
inserted_outbox AS (
    INSERT INTO outbox_events (kafka_topic, kafka_key, payload)
    SELECT 'project.created',
           id::text,
           jsonb_build_object(
               'projectId', id,
               'userId', fk_user_id,
               'name', name
           )
    FROM inserted_project
)
SELECT * FROM inserted_project
```

### The Breakdown
1. `inserted_project`: The core mutating statement. Crucially, the `RETURNING *` exposes the newly generated database-level default fields (like the generated `UUID` and `created_at` timestamp).
2. `inserted_outbox`: We `SELECT FROM inserted_project`, immediately capturing those exact generated properties. We assemble the standard Kafka JSON payload using native `jsonb_build_object` right on the Postgres execution engine! Faster than Node.js `JSON.stringify`!
3. `SELECT`: The original mutation object is passed flawlessly back to the calling TypeScript code, completely agnostic of the background outbox magic.

## The Background Relayer
A highly efficient polling observer, the `OutboxRelay`, loops every 1000m/s on the background thread.
It limits sweeps to 100 entries, immediately pushes the payloads into the actual Kafka Producer buffer, and issues a standard relational `DELETE` to clear the `outbox_events` table continuously, maintaining a near-zero size memory footprint internally despite high throughput bursts.
