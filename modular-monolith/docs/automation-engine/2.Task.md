# Task Automation: Simple Guide

This guide makes it easy to understand and build automations for tasks. We use a simple **"When → If → Then"** pattern.

---

## 1. The Core Pattern

| Part | Description | Example |
| :--- | :--- | :--- |
| **When** | The event that starts the engine. | `Task Updated` |
| **If** | A list of checks. | `Status is DONE` |
| **Then** | What happens next. | `Move to Project X` |

---

## 2. Dealing with Logic (AND/OR)

Think of these as "Checklists":

### ✅ The "ALL" Checklist (AND)
Use this when **EVERY** item must be true.
> *If (Status is DONE) AND (Assigned to Team Support)*

### 💡 The "ANY" Checklist (OR)
Use this when **AT LEAST ONE** item must be true.
> *If (Priority is High) OR (Flagged as Urgent)*

## 3. Common Goal Templates

### A. Auto-Status Transition
"If the team changes to *QA*, move status to *Review*."
```json
{
  "conditions": {
    "field": "teamId", "op": "==", "value": "QA_ID"
  },
  "actions": [
    { "type": "SET_FIELD", "params": { "field": "status", "value": "REVIEW" } }
  ]
}
```

### B. The "Catch-All" Security
"If status is *DONE* but *No Member* is assigned, move back to *TODO*."
```json
{
  "conditions": {
    "all": [
      { "field": "status", "op": "==", "value": "DONE" },
      { "field": "memberId", "op": "is_null", "value": true }
    ]
  },
  "actions": [
    { "type": "SET_FIELD", "params": { "field": "status", "value": "TODO" } }
  ]
}
```

---

## 4. Technical Reference (Simplified)

### Standard Checks (IF)
- `==`: Is exactly.
- `!=`: Is not.
- `changed_to`: Just moved to this value.
- `is_null`: Is empty.

### Action Targets (THEN)
- `@self`: This task.
- `@children`: All sub-tasks.
- `@parent`: The main parent task.

---

## 5. Communication Architecture

To ensure high reliability and isolation, the engine follows a **Dual-Topic Pattern**:

### 5.1 The Logic Lane (`automation.trigger.task`)
- **Purpose**: Dedicated solely to the IFTTT Engine.
- **Payload**: Contains the full `oldState` and `newState` snapshots.
- **Cascading**: This topic is where propagation control happens. If `shouldPropagate` is false, this event is suppressed.

### 5.2 The Display Lane (`project.task.updated`)
- **Purpose**: Feeds the Frontend, Real-time routing, and Analytics.
- **Payload**: Minimal delta required for UI updates.
- **Independence**: This topic always fires regardless of automation logic, ensuring the user's view is never stale.

---

## 6. Pro Tip: Propagation
By default, an automation can trigger *another* automation. If you want a "Dead End" (silent update), add:
`"shouldPropagate": false`
To your action! This will stop the event from firing on the **Logic Lane** but will still update the **Display Lane**.
