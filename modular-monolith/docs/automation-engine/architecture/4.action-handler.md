# Action Handler

This document describes how the Automation Engine executes actions after conditions pass.

---

## Overview

Once a rule's `when` conditions evaluate to `true`, the engine executes the `then` actions **sequentially** — one at a time, in the order they are defined. If an action fails, the sequence stops.

The `ActionDispatcher` (planned: `src/modules/automation/internal/engine/ActionDispatcher.ts`) is the component responsible for:

1. **Resolving** the action's `target` → a concrete list of task IDs
2. **Executing** the `params` update on each resolved task
3. **Controlling propagation** via the `shouldPropagate` flag

---

## Dispatch Context

Every action execution carries a `DispatchContext` object that flows through the entire automation cascade chain:

```typescript
interface DispatchContext {
    triggerTaskId: string;   // The task that triggered the event
    projectId:     string;   // The project the task belongs to
    correlationId: string;   // UUID — traces the full cascade in logs
    depth:         number;   // Increments per cascade hop. Max: 5
}
```

The `depth` counter is the primary safeguard against infinite automation loops.

---

## Target Resolution

Before executing, the dispatcher resolves the `target` direction into a concrete list of task IDs:

| Target | Resolution Strategy | DB Query? |
| :--- | :--- | :--- |
| `@self` | `[triggerTaskId]` — already in context | ❌ No |
| `@parent` | `SELECT parent_task_id FROM project_task WHERE id = ?` | ✅ Yes |
| `@children` | `SELECT id FROM project_task WHERE parent_task_id = ?` | ✅ Yes |
| `@descendants` | `SELECT id FROM project_task WHERE materialized_path LIKE ?` | ✅ Yes |
| `SPECIFIC_TASKS` | `action.targetIds` — already in the rule definition | ❌ No |

> **Note**: `@descendants` uses the materialized path index for performance. See the Task architecture docs for details on how materialized paths work.

---

## Propagation Control (`shouldPropagate`)

After a task is updated by an action, that update itself could trigger another automation. This cascading is intentional but must be controlled.

| `shouldPropagate` | Behaviour |
| :--- | :--- |
| `true` (default) | The updated task emits a new event to the **Logic Lane** (`automation.trigger.task`). Further automations may evaluate on it. `depth` increments. |
| `false` | The update is applied silently. **No event is emitted** to the Logic Lane. The cascade chain is terminated for those tasks. The **Display Lane** (`project.task.updated`) still fires so the UI stays fresh. |

### Cascade Depth Limit

Regardless of `shouldPropagate`, the cascade is **hard-capped at depth 5**. Any automation event with `depth >= 5` is dropped. This is a safety net against misconfigured rules.

```
depth 0 → Initial task mutation
depth 1 → Automation fires on it
depth 2 → That action triggers another
depth 3 → ...
depth 4 → ...
depth 5 → ENGINE HALTS. Event dropped. Warning logged.
```

## Execution Flow (Per-Rule)

```
For each Rule in AutomationPayload (in order):
│
├─ 1. evaluateRuleGroup(oldState, newState, rule.when) → bool
│
├─ [if false] → Skip this rule, continue to next
│
└─ [if true]  → Execute rule.then actions in sequence:
      │
      ├─ For each Action:
      │     ├─ Resolve target → taskIds[]
      │     ├─ Apply params update to each taskId (in-transaction bulk update)
      │     └─ If shouldPropagate: emit outbox event per updated task (depth + 1)
      │
      └─ Continue to next action (or end)
```

---

## Error Handling

- If **target resolution** fails (e.g. task has no parent), the action is skipped. A warning is logged with the `correlationId`.
- If the **bulk update** fails (DB error), the entire action dispatches as a failure and the rule's remaining actions are skipped.
- Failures do **not** roll back the original triggering mutation — the automation runs out-of-band.
