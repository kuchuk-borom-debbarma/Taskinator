# Condition Evaluation

This document describes how the Automation Engine evaluates a rule's `when` block against the before/after state of a task.

---

## Design Principle

The condition evaluator is **completely stateless and pure**. It never touches the database. Given the same inputs, it always produces the same output.

```
evaluateRuleGroup(oldState, newState, ruleGroup) → boolean
```

This is by design. Since we receive `oldState` and `newState` in the Kafka event payload, all the data needed for condition evaluation is already in memory when the engine runs.

---

## Entry Point

```typescript
// src/modules/automation/internal/engine/ConditionEvaluator.ts

evaluateRuleGroup(
    oldState: Record<string, any>,
    newState: Record<string, any>,
    group: RuleGroup
): boolean
```

---

## Evaluation Algorithm

### Step 1: RuleGroup dispatch

The evaluator first checks the `operator` field of the root group:

- `AND` → iterates all rules, short-circuits on the **first failure**
- `OR` → iterates all rules, short-circuits on the **first success**

### Step 2: Child dispatch

For each item in `group.rules`:
- If it has an `operator` field → it is a nested **RuleGroup** → recurse
- Otherwise → it is a **Condition** → evaluate via the `OperatorRegistry`

### Step 3: Operator evaluation

Each `Condition` is dispatched to a pure function via the **OperatorRegistry** — a dictionary mapping:

```typescript
OperatorRegistry[condition.op](oldVal, newVal, expectedVal) → boolean
```

---

## The OperatorRegistry (Strategy Pattern)

Operators are stored as a plain dictionary of pure functions. This makes the evaluator **fully extensible** — adding or removing an operator requires changes in exactly two places:

1. The `Operator` union type in `DSL.ts`
2. The entry in `OperatorRegistry` in `ConditionEvaluator.ts`

No other code changes are needed.

```typescript
export const OperatorRegistry: Record<Operator, OperatorStrategy> = {
    EQUALS:       (_, newVal, val) => newVal === val,
    CHANGED_TO:   (old, newVal, val) => old !== val && newVal === val,
    HAS_CHANGED:  (old, newVal) => old !== newVal,
    IS_NULL:      (_, newVal) => newVal === null || newVal === undefined,
    // ...
};
```

---

## Nested Logic Example

```
Rule: status CHANGED_TO "DONE"
  AND (priority == "HIGH" OR memberId IS_NULL)
```

Evaluation tree:

```
RuleGroup { operator: "AND" }
│
├─ Condition { field: "status", op: "CHANGED_TO", value: "DONE" }  → true/false
│
└─ RuleGroup { operator: "OR" }
       ├─ Condition { field: "priority", op: "EQUALS", value: "HIGH" } → true/false
       └─ Condition { field: "memberId", op: "IS_NULL" }               → true/false
```

The outer `AND` group passes only if:
- The first rule is true **AND**
- At least one rule in the inner `OR` group is true
