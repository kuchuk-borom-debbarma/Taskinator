# 10. GraphQL Architecture (DataLoaders, Modular Schema & Unified Stream)

## Overview
This document outlines the transition from a REST/SSE-based architecture to a unified **GraphQL** layer. The core objectives are to improve frontend developer experience (DX), optimize data fetching through batching, and consolidate all real-time updates into a single, high-performance connection.

---

## 1. Modular Schema & Unified API
All communication flows through a single `/graphql` endpoint, but the schema is organized modularly to ensure domain boundaries are respected.

- **Schema Files**: Located in `src/graphql/schema/*.graphql`. Each domain (Auth, Task, Team, Project, Notification) owns its own Schema Definition Language (SDL) file.
- **Aggregated Resolvers**: Resolvers are grouped by domain in `src/graphql/resolvers/` and aggregated using `@graphql-tools/merge`.
- **Dynamic Loading**: [schema.ts](file:///Users/kuchukboromdebbarma/Documents/projects/Taskinator-v2/modular-monolith/src/graphql/schema.ts) automatically discovers and merges all schema files at runtime.

---

## 2. Optimised Data Fetching: DataLoaders
We solve the **N+1 problem** using the `dataloader` library to implement a **Batching & Caching** layer.

1.  **Batching**: If multiple resolvers request a `User` by ID during a single request, the DataLoader collects those IDs and makes ONE single database query (e.g., `WHERE id IN (...)`).
2.  **Caching**: Per-request caching ensures the same entity is never fetched twice during a single GraphQL execution.

**Loaders Configuration**: See [loaders.ts](file:///Users/kuchukboromdebbarma/Documents/projects/Taskinator-v2/modular-monolith/src/graphql/loaders.ts).

---

## 3. High-Performance Lists: Relay Connections
To support large datasets and 10k RPS scenarios, we follow the **GraphQL Cursor Connection Specification**.

### Why Cursors?
Unlike `offset/limit` pagination, which degrades as skipped row counts grow, **Cursor-based pagination** maintains $O(1)$ or $O(\log N)$ performance. We typically use a compound cursor (e.g., `ISO_DATE|UUID`) to ensure deterministic results.

---

## 4. The Unified Real-time Event Stream
We have replaced multiple domain-specific subscriptions with a single **Unified Event Stream**. This is optimized for high concurrency (10k+ concurrent users).

### Subscription Flow:
1.  **Single Connection**: The frontend establishes exactly **one** SSE connection via the `realtimeStream` subscription.
2.  **Union Type**: The stream yields a `RealtimeEvent` union, which can be `TaskCreated`, `TaskUpdated`, `TaskDeleted`, or `InternalNotification`.
3.  **Horizontal Fan-out**:
    -   Changes are published to **Kafka**.
    -   Each modular-monolith instance has an ephemeral `RealtimeKafkaConsumer` that fans out Kafka messages to a local `PubSub` engine.
    -   The GraphQL subscription resolver filters this local feed by `projectId` and `userId` before pushing to the browser.

**Benefits**: Reduced file descriptor usage, lower TCP overhead, and instant updates across all browser tabs.

---

## 5. Security & Authentication
- **Initial Verification**: JWTs are extracted from the `Authorization` header or a `?token=` query parameter (for SSE/Subscriptions).
- **Context**: The verified `userId` is injected into the [GraphQLContext](file:///Users/kuchukboromdebbarma/Documents/projects/Taskinator-v2/modular-monolith/src/graphql/context.ts).
- **Authorization**: Individual resolvers are responsible for checking ownership or membership before returning data.

---

## 6. Lifecycle & Boot Sequence
To prevent "cold start" event loss, the application follows a strict **4-Phase Boot Sequence**:

1.  **Phase 1 (Infrastructure)**: Connect to Kafka and ensure all topics exist.
2.  **Phase 2 (Domain)**: Initialize all domain services and join Kafka consumer groups.
3.  **Phase 3 (Public API)**: The Express/GraphQL server only starts listening once all consumers are ready.
4.  **Phase 4 (Relay)**: The Outbox Relay starts processing transactional events.

Reference: [index.ts](file:///Users/kuchukboromdebbarma/Documents/projects/Taskinator-v2/modular-monolith/src/index.ts).

---

## 7. Performance & Scaling (10k RPS)
- **Batched Inserts**: We use `REWRITE_BATCHED_INSERTS` and `unnest` in SQL for high-volume notifications.
- **Connection Stewardship**: The Unified Stream minimizes the blast radius of real-time connections on load balancers.
- **Optimistic Locking**: Every mutation requires a `version` column to prevent stale-write overwrites during high concurrency.
