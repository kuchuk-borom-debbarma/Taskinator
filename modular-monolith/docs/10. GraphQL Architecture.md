# 10. GraphQL Architecture (DataLoaders, Connections & Subscriptions)

## Overview
This document outlines the transition from a REST/SSE-based architecture to a unified **GraphQL** layer. The core objectives are to improve frontend developer experience (DX), optimize data fetching through batching, and unify real-time updates under a single type-safe interface.

---

## 1. Unified API Entry Point
Instead of multiple REST endpoints (`/projects`, `/teams`, `/tasks`, `/realtime/stream`), all communication now flows through a single `/graphql` endpoint.

- **Status**: Co-exists with REST for backward compatibility.
- **Transport**: Standard HTTP (POST) for Queries/Mutations and SSE for Subscriptions.

---

## 2. Optimised Data Fetching: DataLoaders
A common problem in GraphQL (and nested REST calls) is the **N+1 problem**. For example, fetching 10 tasks and then making 10 separate calls to fetch the user implementation for each task.

### How DataLoaders Solve This:
We use the `dataloader` library to implement a **Batching & Caching** layer:
1.  **Batching**: If multiple resolvers request a `User` by ID during a single request, the DataLoader collects those IDs and makes ONE single database query (e.g., `WHERE id IN (...)`).
2.  **Caching**: If the same ID is requested twice in the same request, the second call is served instantly from memory.

**Impact**: Database round-trips are reduced by up to 90% for complex nested views.

---

## 3. High-Performance Lists: Relay Connections
To support large datasets (e.g., thousands of tasks), we follow the **GraphQL Cursor Connection Specification** (often called Relay Connections).

### Structure:
```graphql
tasks(first: 10, after: "cursor") {
  edges {
    node {
      id
      title
    }
    cursor
  }
  pageInfo {
    hasNextPage
    endCursor
  }
  totalCount
}
```

### Why Cursors?
Unlike `offset/limit` pagination, which degrades in performance as you skip more rows, **Cursor-based pagination** (using `materializedPath` or `createdAt` indices) maintains $O(1)$ or $O(\log N)$ performance regardless of the page depth.

## 4. Real-time Subscriptions (SSE Replacement)
We are replacing the manual `SSEManager.ts` with **GraphQL Subscriptions over SSE**.

### The Architecture:
1.  **PubSub Engine**: We use `graphql-yoga`'s `createPubSub` to handle local event broadcasting.
2.  **Kafka Bridge**: The existing `RealtimeKafkaConsumer` (which handles the distributed fan-out across server instances) now acts as the "Publisher" for our GraphQL PubSub engine.
3.  **Delivery**: When a Kafka message arrives, the server checks its active GraphQL Subscriptions and pushes the data to the connected browser.

### Benefits:
- **Automatic Reconnects**: Handled by modern GraphQL clients (like Urql or Apollo).
- **Graceful Failover**: No manual heartbeat logic needed; the GraphQL server handles stream health.
- **Filtering**: Clients can subscribe to specific projects or events using standard GraphQL arguments.

---

## 5. Security & Authentication
- **Initial Verification**: The JWT is extracted from the `Authorization` header.
- **Context Injection**: The `userId` is injected into the GraphQL Context, making it available to every resolver.
- **Authorization**: Individual resolvers check project/team memberships (cached in DataLoaders) before returning sensitive data.
