# 9. Real-time Architecture (Server-Sent Events)

## Overview
To provide a premium, collaborative experience, Taskinator requires real-time updates for notifications and task modifications. **Server-Sent Events (SSE)** were chosen for their unidirectional efficiency, native browser support for reconnection, and lower computational overhead compared to WebSockets for our specific push-only use cases.

The system is architected to handle **10,000 concurrent connections** across a horizontally scalable cluster.

## 1. The Multi-Instance Fan-Out Problem
In a clustered environment (e.g., K8s with 5 replicas), User A might be connected to Instance 1, while the event that affects User A (e.g., a Task Update) is processed by Instance 3.

### The Solution: Unique Consumer Groups
Unlike standard background workers that use a shared `groupId` to load-balance work, the **Realtime Service** on every instance initializes with a **stochastically generated, unique Group ID**:
- `groupId: "realtime-fanout-${hostname}-${uuid}"`

This instructs Kafka to treat every server instance as a separate logical consumer group. Consequently, **every instance receives every message** from the `project.task` and `internal-notification` topics. 

### Filtering Logic
Once a message arrives at an instance:
1.  The `RealtimeKafkaConsumer` parses the payload.
2.  It queries the local `SSEManager`'s in-memory registry.
3.  If the targeted `userId` (or users in `projectId`) are connected to **this specific instance**, the message is pushed over the established HTTP stream. 
4.  Otherwise, the message is ignored.

## 2. Low-Level Connection Management

### Registry Structure
We utilize a two-tier nested collection for $O(1)$ lookup and memory efficiency:
```typescript
// Map<userId, Set<Response>>
private registry = new Map<string, Set<Response>>();
```
A `Set` is used for `Set<Response>` because a single user might have multiple tabs open. If User A has 3 tabs, Instance 1 will send the event to all 3 `Response` objects simultaneously.

### The Lifecycle of an SSE Stream
When a client hits `GET /api/v1/realtime/stream`:

1.  **Handshake**:
    ```http
    HTTP/1.1 200 OK
    Content-Type: text/event-stream
    Cache-Control: no-cache, no-transform
    Connection: keep-alive
    X-Accel-Buffering: no  # Prevents Nginx from buffering the stream
    ```
2.  **Initial Payload**: An empty `:ok` comment to confirm the stream is open.
3.  **Active Monitoring**: The server listens for `req.on('close')`.
4.  **Cleanup**: When the connection closes (navigation or tab kill), we MUST remove the `Set` entry and, if the `Set` becomes empty, delete the `userId` key from the `Map` to prevent "Ghost Connection" memory leaks.

## 3. Optimizing for 10k RPS Infrastructure

### Resource Constraints
Every SSE connection is a TCP socket. To support 10k connections:
- **File Descriptors**: The OS `ulimit -n` must be increased to >10,000.
- **Node.js/Bun Event Loop**: Since connections are mostly idle (parked), the primary CPU cost is the **30s heartbeat**.

### Heartbeat Strategy
To prevent intermediate proxies (Nginx, AWS ALB, Cloudflare) from closing "idle" connections, the `SSEManager` runs a global interval:
```typescript
setInterval(() => {
    for (const connections of this.registry.values()) {
        connections.forEach(res => res.write(':heartbeat\n\n'));
    }
}, 30000);
```
*Note: Heartbeats use the SSE comment syntax (`:`) which is ignored by the browser's `onmessage` handler but keeps the TCP connection active.*

## 4. Message Framing & Re-sync

### SSE Framing
Events follow the RFC 6797 standard:
```text
id: <uuid>
event: task_updated
data: {"id": "...", "version": 5}
\n\n
```

### The "Gap" Protection (Future)
Since SSE is unidirectional, if a user disconnects for 5 seconds, they might miss an event. 
- **Signal-only pattern**: We push an "Invalidation Signal" (e.g., `TASK_LIST_STALE`).
- **Re-sync**: On reconnection, the frontend hook (`useRealtime`) automatically triggers a React-Query `refetch()`, ensuring the UI converges to the latest state regardless of missed events.

## 5. Security Handshake
Browsers do not support custom headers in the `new EventSource(url)` constructor.
1.  Frontend passes JWT in the query string: `/stream?token=ey...`
2.  `requireAuth` middleware extracts and verifies the token.
3.  The `userId` is attached to the request, and the stream is promoted.
