# 9. Real-time Architecture (Server-Sent Events + Kafka Fan-out)

## Overview
To provide a premium, collaborative experience, Taskinator requires real-time updates for notifications and task modifications. The architecture leverages **Server-Sent Events (SSE)** for edge delivery and **Kafka** for distributed signaling, specifically optimized for **10,000 active connections** in a horizontally scaled environment.

---

## 1. The Distributed Connection Constraint
A critical technical constraint of any real-time system (SSE or WebSockets) is that the **physical TCP socket lives only in the memory of the specific server instance it connected to.**

- **Problem**: If `User A` is connected to `Server 1`, then `Server 2` has no physical way to "write" to `User A`'s browser.
- **The Redis Fallacy**: It is a common mistake to think Redis can "store" these connections. Redis can only store *metadata* (e.g., "User A is at Server 1"). To send a message, `Server 2` would still have to send a signal to `Server 1`.

---

## 2. Distributed Signaling: Kafka Fan-out Pattern
Rather than adding a secondary "Signaling Layer" like Redis Pub/Sub, we leverage our existing **Kafka backbone**. Since all domain changes are already emitted to Kafka via the Outbox Relay, we use Kafka as the **Global Broadcast Bus**.

### Unique Group ID Strategy
In a standard worker (e.g., `TaskService`), multiple instances share a `groupId` to load-balance work. **In the Real-time Service, we do the opposite.**

- Every server instance generates a **unique, ephemeral Group ID** on startup:
  `groupId: "realtime-fanout-${hostname}-${uuid}"`
- **Effect**: This instructs Kafka to treat every instance as an independent consumer. When a message (e.g., `TASK_UPDATED`) is published, **Kafka multicasts it to every single server instance in the cluster.**

---

## 3. The Local "Connection Registry"
Each server maintains a high-speed, $O(1)$ in-memory index:
1. **User Registry**: `Map<userId, Set<Response>>`
2. **Project Index**: `Map<projectId, Set<userId>>`

### How an Event Propagates (Step-by-Step)
1.  **Change**: A user updates a task. A wCTE atomically writes the change and an `outbox_event` to PostgreSQL.
2.  **Relay**: The `OutboxRelay` polls the DB and publishes to Kafka topic `project-task-events`.
3.  **Broadcast**: Kafka multicasts this message to `Server A`, `Server B`, and `Server C` (all having unique Group IDs).
4.  **Local Filtering**:
    - `Server A` receives the message. It checks its **Local Map**. If no connected user belongs to that project, it drops the message immediately (sub-microsecond overhead).
    - `Server B` receives the message. It finds 10 users in its **Local Map** who belong to that project. It iterates through their pinned `Response` objects and writes the SSE frame.
5.  **Delivery**: The browsers connected to `Server B` see the update instantly.

---

## 4. Why this is the "Highly Performance" Path

### High Throughput (10k RPS)
By using Kafka as the signaling bus, we eliminate the need for:
- Inter-service RPC calls (e.g., Server B trying to find Server A).
- Redis Pub/Sub overhead (reducing the total number of moving parts in the stack).
- Global state synchronization (which introduces consistency bottlenecks).

### Zero-Latency Local Access
Retrieving a connection from an in-memory `Map` is significantly faster than a network-bound Redis lookup. This ensures that even under a load of 10,000 connections, the time from "Kafka Message Received" to "Browser Pulse" is nearly instantaneous.

### Resilience
Since Kafka provides **Durability**, if a backend instance restarts, it can potentially "replay" or "catch up" on missed real-time signals by managing its own offsets, ensuring no notification is lost during brief network partitions.

---

## 5. Security & Isolation
- **Authentication**: JWT is verified during the SSE handshake (supporting both `Authorization` header and `?token=` query param).
- **Privacy**: Even though every server receives every message, the server only delivers to users who have **Project Membership**, which is verified and cached in the SSE Manager the moment the connection is established.

---

## 6. Stability & Connection Tuning
To maintain 10,000+ stable, long-lived connections, specific Node.js/Express socket configurations are required to prevent premature drops:

### Socket Configuration
- **`req.socket.setTimeout(0)`**: Disables the default Node.js socket timeout (usually 120s). This is critical for SSE to prevent the server from killing "idle" streams that haven't sent an update recently.
- **`req.socket.setKeepAlive(true, 1000)`**: Enables TCP-level keep-alive pulses. This helps the connection survive NAT timeouts, aggressive firewalls, and intermediate load balancers (ALB/Nginx).
- **`req.socket.setNoDelay(true)`**: Disables Nagle's algorithm to ensure that SSE frames (which are small) are sent immediately without waiting for buffer fills.

### Buffer Control
- **`X-Accel-Buffering: no`**: Essential for Nginx/Proxy compatibility. It tells the proxy not to buffer the response, ensuring that each `data:` frame reaches the browser the moment it is written.
- **`res.flushHeaders()`**: Called immediately after `res.writeHead()`. This forces the initial HTTP headers out to the browser so the `EventSource` enters the `OPEN` state instantly, rather than waiting for the first domain event.

### Common Errors & Troubleshooting
- **`ERR_INCOMPLETE_CHUNKED_ENCODING`**: Usually occurs if the server sends the headers for a chunked response but closes the socket before the body is ready. Fixed by disabling timeouts and ensuring `res.write()` is not called after `res.end()`.
- **Handshake Failures**: Always verify that the `Logger` implementation supports `.debug()` as the handshake process is verbose for monitoring purposes.
