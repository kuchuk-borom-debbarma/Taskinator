# 19. Atomic Event Orchestration

This document describes the architectural patterns used in Taskinator to ensure **Exactly-Once Delivery** and **Exactly-Once Processing** across the modular monolith.

## 1. Overview
In a distributed event-driven system, failure is inevitable. A process can crash after writing to a database but before sending a message to Kafka, or it can crash after processing a message but before committing the offset.

To solve this, Taskinator uses two complementary atomic patterns:
1.  **Atomic Sink (Producers)**: Ensuring the event is *always* captured when the database changes.
2.  **Atomic Claim (Consumers)**: Ensuring an event is *never* processed more than once by the same module.

---

## 2. The "Atomic Sink" Pattern (Command Side)
Used in **Service Layer / Queries** to eliminate the "Dual Write" problem.

### How it works
Instead of separate database and Kafka calls, we use **Data-Modifying CTEs (wCTEs)** in PostgreSQL. This wraps the business logic and the Outbox entry into a single atomic transaction at the database engine level.

### Example: `insertTeam`
```sql
WITH inserted_team AS (
    INSERT INTO project_team (name, fk_project_id, fk_user_id)
    VALUES (${name}, ${projectId}, ${actorId})
    RETURNING id, name, fk_project_id
),
inserted_outbox AS (
    INSERT INTO outbox_events (kafka_topic, kafka_key, payload)
    SELECT 
        'team-events', -- Physical Topic
        id::text,      -- Kafka Partition Key
        jsonb_build_object(
            'type', 'team.created', -- Explicit Event Type
            'teamId', id,
            'name', name
        )
    FROM inserted_team
)
SELECT * FROM inserted_team;
```

### Key Benefits
*   **Zero-Loss**: If the team is created, the outbox entry is *guaranteed* to exist.
*   **Performance**: One single round-trip to the database handles both domain state and messaging.
*   **Relay Independence**: The `OutboxRelay` simply moves data from the table to Kafka; it contains no business logic.

---

## 3. The "Atomic Claim" Pattern (Listener Side)
Used in **Module Listeners** to ensure idempotency.

### How it works
Every listener manages its own `db.transaction()`. Before performing any business logic, it attempts to "claim" the batch of events by inserting markers into the `processed_event` table.

### The `processed_event` Table
```sql
CREATE TABLE processed_event (
    event_id TEXT,
    consumer_group TEXT,
    processed_at TIMESTAMPTZ DEFAULT NOW(),
    PRIMARY KEY (event_id, consumer_group)
);
```

### The Logic: `claimEventsAtomic`
```typescript
await db.transaction().execute(async (trx) => {
    // [1] Atomic Check-and-Commit
    const unprocessed = await claimEventsAtomic(trx, events, 'my-consumer-group');
    
    // If all events were already processed, exit early
    if (unprocessed.length === 0) return;

    // [2] Execute Business Logic
    await performCleanup(unprocessed, trx);
    
    // [3] Final Commit
    // Both the 'processed_event' markers and business changes commit together.
});
```

### Why this is Robust
*   **Resilience to Crashes**: If the process crashes during `performCleanup`, the transaction rolls back. The `processed_event` marker is deleted, allowing the next Kafka retry to succeed.
*   **Duplicate Prevention**: If Kafka sends the same message twice (at-least-once delivery), the second attempt will fail the `INSERT` in `claimEventsAtomic` (due to the Primary Key), and the business logic will never run again.

---

## 4. The Event Lifecycle (End-to-End)

| Stage | Action | Atomicity |
| :--- | :--- | :--- |
| **Command** | User calls `createTeam()` | **Atomic Sink**: DB record + Outbox entry created. |
| **Relay** | `OutboxRelay` sweeps entry | **At-Least-Once**: Retries until Kafka ACKs. |
| **Broker** | Kafka stores message | **Durable**: Replicated across partitions. |
| **Listener** | `claimEventsAtomic()` | **Atomic Claim**: Marks event as "seen" in local DB. |
| **Domain** | Business Logic executes | **Consistent**: Uses same `trx` as the claim. |
| **Commit** | DB Transaction Finishes | **Final**: Changes + Marker persisted. |

---

## 5. Implementation Rules
1.  **Never Use Auto-Transactions**: Always wrap listener logic in an explicit `db.transaction().execute()`.
2.  **Pass the Transaction**: Ensure all queries inside a listener use the `trx` instance, not the global `db` instance.
3.  **Specific Group IDs**: Use unique `consumer_group` names in `claimEventsAtomic` to allow different modules to process the same event stream independently.
4.  **Batch Support**: Always handle events as arrays to maintain the system's 10k RPS performance target.
