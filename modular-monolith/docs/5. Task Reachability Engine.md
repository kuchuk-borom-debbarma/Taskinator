# Task Reachability Engine: Closure Table Pattern

This document details the architecture for maintaining the `task_reachability` index using a standard Closure Table pattern.

## 1. The Core Idea: Closure Table
Instead of complex path counting, we use a transitive closure table that stores every path from every ancestor to every descendant in the graph.

**Our Schema**:
- `ancestor_task_id`
- `descendant_task_id`
- `depth`: The number of hops between the nodes.

This allows for extremely fast reachability checks (O(1)) and graph traversal by querying the index directly.

---

## 2. The Implementation Logic

### A. Link Creation (Expansion)
When a link `A -> B` is created:
1.  **Discover**:
    - All tasks that reach **A** (Ancestors of A + A itself).
    - All tasks reached by **B** (Descendants of B + B itself).
2.  **Cross-Join**: Every ancestor now reaches every descendant.
3.  **Update**:
    - `New_Depth = Depth(Anc -> A) + 1 + Depth(B -> Des)`
    - Insert new records into `task_reachability`.
    - If a path already exists, we maintain the record.

### B. Link Removal (Contraction)
When a link `A -> B` is removed, we must repair the closure without the bridge.
1.  **Identify**: Find all pairs `(Anc, Des)` where the path potentially went through `A -> B`.
2.  **Purge**: Remove the transitive connections.
3.  **Re-Verify**: Since multiple paths might exist, we perform a scoped check to see if any other link still connects the affected sub-graphs and restore reachability where necessary.

### C. Task Deletion
1.  **Purge**: Remove all rows where the deleted task is either an ancestor or a descendant.
2.  **Repair**: Trigger a scoped repair for any tasks that were previously connected through the deleted node.

---

## 3. Signal Architecture
We use declarative signals in the `TASK_AGGREGATED` topic to trigger these repairs:

| Signal | Payload | Logic |
| :--- | :--- | :--- |
| `SYNC_TASK_REACHABILITY` | `sourceId, targetId, action` | Expand or contract the closure table based on link change. |
| `DELETE_TASK_REACHABILITY` | `taskIds[]` | Purge nodes and repair fragmented paths. |

---

## 4. Performance & Scalability
- **Idempotency**: All insertions use `ON CONFLICT DO NOTHING` to ensure stable state.
- **Batching**: The listener processes link changes in a single transaction.
- **Counter Sync**: Following any change, we update `total_incoming_count` and `total_outgoing_count` in the `project_task` table for immediate UI feedback.
