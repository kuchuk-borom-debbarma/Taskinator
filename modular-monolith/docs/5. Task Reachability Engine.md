# Task Reachability Engine: Incremental Path-Counting

This document details the architecture for maintaining the `task_reachability` index using a high-performance, event-driven approach.

## 1. The Core Idea: Path-Counting
The fundamental challenge of graph reachability is **accurate repair**. If you only store a boolean `is_reachable`, you don't know if it's safe to delete a connection when a path breaks.

**Our Solution**: Every reachability record stores a `path_count`.
- If there are 3 different ways to get from Task A to Task D, the `path_count` is 3.
- If one path is deleted, the count becomes 2. We **keep** the record.
- We only delete the reachability record when `path_count` hits **0**.

This allows for localized, incremental updates without ever needing to re-scan the entire global graph.

---

## 2. The Implementation Logic

### A. Link Creation (Expansion)
When a link `A -> B` is created, we bridge the gap between two existing sub-graphs.

1.  **Discover**:
    - All tasks that reach **A** (Ancestors).
    - All tasks reached by **B** (Descendants).
2.  **Cross-Join**: Every ancestor now reaches every descendant.
3.  **Update**:
    - `New_Paths = PathCount(Anc -> A) * PathCount(B -> Des)`
    - `Reachability(Anc -> Des).path_count += New_Paths`

### B. Link Removal (Contraction)
When a link `A -> B` is removed, we perform the inverse of the expansion.

1.  **Subtract**: We run the same cross-join but **decrement** the `path_count`.
2.  **Purge**: Any record where `path_count <= 0` is hard-deleted from the database.

### C. Task Deletion (Bulk Repair)
Deleting a task is essentially a batch removal of all its direct links.
1.  **Identify**: Find all direct links connected to the deleted task.
2.  **Contract**: Run the Link Removal logic for every identified link.
3.  **Cleanup**: Final hard-purge of any row where the deleted task is an ancestor or descendant.

---

## 3. Signal Architecture
We use declarative signals in the `TASK_AGGREGATED` topic to trigger these repairs:

| Signal | Payload | Logic |
| :--- | :--- | :--- |
| `SYNC_TASK_REACHABILITY` | `sourceId, targetId, action` | Trigger Expansion or Contraction for a single link. |
| `DELETE_TASK_REACHABILITY` | `taskIds[]` | Trigger Bulk Repair for deleted nodes. |

---

## 4. Performance & Scalability
- **Idempotency**: All updates use `ON CONFLICT` logic to ensure that out-of-order Kafka events don't corrupt the counts.
- **Batching**: The listener processes multiple reachability signals in a single database transaction.
- **Project Isolation**: All queries are strictly scoped by `fk_project_id` to prevent cross-tenant performance interference.
- **Counter Repair**: Following any reachability change, we sync the `total_incoming_count` and `total_outgoing_count` in the `project_task` table for immediate UI feedback.
