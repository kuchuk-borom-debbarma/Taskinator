# 17. Explicit Kafka Architecture (Zero-Magic)

Traceability and predictability are paramount in a Modular Monolith. Taskinator moved from a "Magic Topic Discovery" system to an **Explicit Messaging API** to eliminate hidden complexities and improve developer ergonomics.

## 1. Rationale for Change
Previously, the system used a hidden `EVENT_TO_TOPIC` mapping table. Calling `eventBus.publish('EVENT_TYPE', payload)` would internally look up which topic should receive that event. 

While convenient, this caused several issues at scale:
- **Opaque Flow**: Finding which topic emitted a specific event required deep-diving into infrastructure code.
- **Traceability Gaps**: Logs only showed the event type, making it hard to debug producer/consumer mismatches across module boundaries.
- **Bootstrapping Complexity**: The entire mapping table had to be synchronized and validated at startup.

## 2. The "Zero-Magic" API
We now require the **Physical Kafka Topic** to be specified at every entry point. This makes the system "Explicit over Implicit."

### Publishing
```typescript
await eventBus.publish(
    KAFKA_TOPICS.PROJECT,           // Topic: "project-events"
    KAFKA_EVENTS.PROJECT.CREATED,   // Type: "PROJECT.CREATED"
    { projectId, userId }           // Payload
);
```

### Subscribing
```typescript
await eventBus.subscribe(
    KAFKA_TOPICS.PROJECT,           // Source Topic
    'consumer-group-name',          // Group
    { [KAFKA_EVENTS.PROJECT.CREATED]: handler }, // Event map
    { batch: true }                 // Options
);
```

## 3. The "Batch Aggregator" Pattern
This explicit design enables a clear, tiered processing strategy:

1. **Domain Topics** (`project-events`, `task-events`): Raw, high-volume transactional streams.
2. **Aggregated Topics** (`project-aggregated-events`): Refined, "clean" data signals published by Coordinators.

By naming the listeners based on their source (e.g., `ProjectAggregated_TaskCleanupListener`), we create a "Mental Map" of the data flow that is visible directly in the directory structure and application logs.

## 4. Operational Benefits
- **Debugging**: If a message is missing, you know exactly which Topic to inspect in Kafka without checking a mapping table.
- **Schema Evolution**: Adding new events no longer requires updating a central registry; simply publish to the relevant topic.
- **Performance**: Zero overhead for topic lookups during high-volume `wCTE` outbox insertions.
