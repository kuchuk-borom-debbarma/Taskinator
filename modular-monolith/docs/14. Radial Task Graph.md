# 14. Radial Task Graph (Neural Lattice)

The **Radial Task Graph**, also known as the **Neural Lattice**, is a high-performance discovery engine designed to visualize task dependencies in a modular, mind-map-like interface. Unlike a traditional list or board view, it focuses on the "reachability" and "flow" of tasks.

## 1. Core Objectives
- **Contextual Clarity**: Always keep one task at the center, showing how it relates to its immediate and distant neighbours.
- **Bi-Directional Discovery**: Seamlessly discover both ancestors (blockers) and descendants (follow-ups) in a single view.
- **Infinite Scalability**: Use cursor-based pagination and radial depth limits to allow continuous expansion without overwhelming the client or database.

## 2. Technical Architecture

### A. Two-Step Discovery Process
To maximize performance, the graph is hydrated in two distinct steps:

1.  **Step 1: Node Discovery**:
    - The server queries the `task_reachability` closure table.
    - It finds all nodes within `maxDepth` (default 3, cap 5) of the `focusedTask`.
    - It deduplicates nodes that are both ancestors and descendants and assigns a `min_depth` and `direction`.
    - Result: A paginated list of `NeighbourRecord` objects (lightweight IDs + metadata).

2.  **Step 2: Edge & Data Hydration**:
    - **Links**: The server fetches all `task_link` records where at least one end-point is in the current discovery set. This ensures all relevant connections (cross-links) are visible.
    - **Tasks**: GraphQL DataLoaders are used to hydrate the full task metadata (title, status, etc.) for every discovered ID in a single batched database trip (O(1) database overhead).

### B. Reachability & Directionality
The system categorizes neighbours into three directions:
- `incoming`: Tasks that lead *to* the focused task (Ancestors).
- `outgoing`: Tasks that follow *from* the focused task (Descendants).
- `both`: Tasks that are reachable in both directions (rare, usually indicates a cycle or complex hierarchy).

## 3. Data Integrity & Security

### Authorization
Every segment of the graph discovery process is wrapped in a **CTE-based auth check**. A user can only see a neighbourhood if they have membership or ownership of the parent project.

### Optimistic Geometry
The server performs the **Arrangement**: it tells the client exactly how deep each node is and what direction it belongs to. This allows the frontend to apply a radial layout algorithm immediately upon receiving the data, rather than traversing the tree manually.

## 4. API Specification

### Query: `taskNeighbourhood`
```graphql
query {
  taskNeighbourhood(
    projectId: "...",
    taskId: "...",
    maxDepth: 3,
    first: 20
  ) {
    focusedTask { ... }
    nodes {
      task { ... }
      depth
      direction
    }
    edges {
      id
      sourceTaskId
      targetTaskId
      label
    }
    pageInfo { ... }
  }
}
```
