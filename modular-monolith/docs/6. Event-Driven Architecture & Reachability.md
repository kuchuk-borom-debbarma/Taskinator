# Taskinator: Event-Driven Architecture & Reachability Engine

This document details the high-performance orchestration engine and the transitive reachability system used in the Taskinator modular monolith.

## 1. The EDA Pipeline: "Action-Oriented Signaling"

We use a strictly decoupled, asynchronous signaling model to maintain data consistency across modules (Projects, Teams, Tasks, Auth) without distributed transactions.

### A. The Monotonic Outbox
Every domain event (e.g., `TASK_CREATED`) is written to the `outbox_events` table within the same transaction as the domain change.
- **Strict Sequencing**: The `id` column is a `BIGSERIAL`. This ensures that the background Outbox Relay publishes events to Kafka in the exact order they were committed.
- **Deterministic Ordering**: Listeners and Aggregators rely on this sequence to prevent "Zombie Node" race conditions (e.g., trying to link a task before it's "created").

### B. Smart Aggregation (The "Brain")
Aggregators (e.g., `TaskEvents_BatchAggregator`) act as stateless orchestrators. They:
1. **Chronological Sort**: Sort inbound batches by `timestamp` to ensure causality is preserved.
2. **Semantic Folding**: Minimize downstream churn by canceling out opposite events (e.g., a +1 and -1 count change for the same project in one batch result in zero signals).
3. **Declarative Signaling**: Emit atomic command signals (e.g., `SYNC_TEAM_TASK_COUNT`, `DELETE_TASK_REACHABILITY`) instead of raw events.

### C. Atomic Listeners
Listeners (e.g., `ReachabilitySyncListener`) follow a strict execution pattern:
- **Idempotency**: Use `claimEventsAtomic` to ensure no signal is processed twice.
- **Atomic Sink**: Perform the domain update (e.g., graph repair) in a local transaction.

## 2. The Task Reachability Engine

We use a **Closure Table** pattern to provide $O(1)$ transitive lookup performance while maintaining graph integrity.

### A. Schema Design
Table: `task_reachability`
- `ancestor_task_id`, `descendant_task_id`: Transitive endpoints.
- `depth`: Distance between nodes (used for shortest-path resolution).
- **No Path Counting**: We prioritize database simplicity and use a "Repair" strategy for deletions to handle overlapping paths (Diamonds).

### B. Graph Maintenance Strategies

#### 1. Expansion (Link ADD)
**Algorithm**: Bridge Cross-Join.
When link `A -> B` is added, we find all ancestors of `A` and all descendants of `B` and cross-join them.
- **Complexity**: $O(Ancestors \times Descendants)$.
- **Implementation**: Performed in a single `INSERT ... SELECT` statement.

#### 2. Contraction (Link REMOVE)
**Algorithm**: Purge & Recursive Repair.
When link `A -> B` is removed:
1. **Purge**: Delete all paths `(X, Y)` where `X` reaches `A` and `B` reaches `Y`.
2. **Repair**: Run a **Recursive CTE** starting from the affected ancestors to re-discover any valid alternative paths. This ensures "Diamond" structures remain intact.

#### 3. Bulk Node/Project Deletion
- **Task Deletion**: Purges all transitive rows involving the deleted tasks and repairs the fragmented sub-graphs.
- **Project Deletion**: Performs a high-performance hard delete of all reachability rows associated with the `fk_project_id`.

## 3. Consistency Guarantees

| Scenario | Strategy | Guarantee |
| :--- | :--- | :--- |
| **Out-of-Order Kafka** | Chronological Aggregator Sorting | Causal Ordering |
| **Network Retries** | BIGSERIAL sequencing + Idempotency | Exactly-Once Processing |
| **Overlapping Paths** | Recursive Repair (CTE) | Graph Integrity (No Zombies) |
| **System Crash** | Transactional Outbox | Eventual Consistency |

## 4. Performance Profile
- **Lookups**: $O(1)$ via simple index seek on `task_reachability`.
- **Additions**: High (Single SQL statement).
- **Deletions**: Medium (Recursive repair is scoped to the affected sub-graph).
- **Throughput**: Optimized for **10k RPS** via batching and semantic folding.
