# Smart Event Processing Architecture

Taskinator implements a high-performance **Smart Batching** strategy for its domain event consumers. This architecture is designed to handle 10k+ RPS by minimizing database round-trips and avoiding redundant calculations through event "folding."

## 1. The Core Problem
At extreme scale, every database transaction is expensive. If the system processes events one-by-one, it often encounters:
- **IOPS Bottlenecks**: High disk activity from thousands of small updates.
- **Lock Contention**: Multiple consumers trying to update the same row (e.g., a project's `tasks_count`) at the same time.
- **Redundant Work**: Processing a "Create" event for an entity that was deleted milliseconds later.

## 2. The Smart Batching Pipeline

To solve this, we use a multi-stage aggregation pipeline:

### Stage A: Ingestion (Transport)
The `KafkaBus` fetches a raw batch of messages from the broker. If the consumer registers with `{ batch: true }`, it receives the entire array of events for that topic at once.

### Stage B: Folding (Semantic Cancellation)
The domain consumer (e.g., `ProjectTopicConsumer`) analyzes the batch in memory. It applies **State Folding**:
- `CREATED` (+1) + `DELETED` (-1) = **0 (Cancelled)**
- Two operations on the same entity within the same 100ms batch negates each other, and they are never sent to the database.

### Stage C: Aggregation (Non-Blocking)
The net impact of the batch is calculated (e.g., "User A net-gained 3 projects"). To keep the main consumer loop fast, the results are published as a single **Aggregated Event** to a new internal topic.

### Stage D: Execution (Asynchronous Update)
A dedicated listener in the target domain (e.g., `ProjectAggregatedListener` in the Auth module) consumes the aggregated event and performs a **Single Bulk SQL Query** to synchronize the database.

## 3. High-Performance SQL Pattern
The system uses the `VALUES` join pattern to update multiple rows in one trip:

```sql
UPDATE users SET 
    projects_count = users.projects_count + v.delta
FROM (
    SELECT * FROM UNNEST($1::uuid[], $2::int[])
) AS v(id, delta)
WHERE users.id = v.id;
```

## 4. Scaling Benefits
- **Database IO**: Reduced by up to 100x depending on batch density.
- **Locking**: Row-level locks are held for much shorter durations and in organized batches.
- **Throughput**: Linear scaling with Kafka partitions while maintaining transactional integrity within each batch.
