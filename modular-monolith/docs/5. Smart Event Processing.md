# 5. Smart Event Processing Architecture

Taskinator implements a high-performance **Smart Batching** strategy for its domain event consumers. This architecture is designed to handle 1,000+ RPS per topic by minimizing database round-trips and avoiding redundant calculations through event "folding."

## 1. The Core Problem
At extreme scale, every database transaction is expensive. If the system processes events one-by-one, it often encounters:
- **IOPS Bottlenecks**: High disk activity from thousands of small updates.
- **Lock Contention**: Multiple consumers trying to update the same row (e.g., a project's `tasks_count`) at the same time.
- **Redundant Work**: Processing a "Create" event for an entity that was deleted milliseconds later in the same batch.

## 2. The Coordinator-Handler Pattern
To maintain high performance and clean code, we use a **Coordinator-Handler** architecture.

### Stage A: Batch Aggregation (The Coordinator)
The `ProjectEvents_BatchAggregator` consumes raw events from the `project-events` topic. It performs **Semantic Folding**:
- `CREATED` (+1) + `DELETED` (-1) = **0 (Cancelled)**. 
- If an entity is created and deleted within the same 100ms batch, the operations negate each other in memory and never touch the database.

### Stage B: Modular Workers (The Handlers)
Once the batch is "folded," the Coordinator calculates the net deltas. It then delegates "Clean Data" to specialized handlers:
- **`UserProjectCountHandler`**: Receives a `Map<userId, delta>`.
- **`ProjectCleanupHandler`**: Receives a `string[]` of deleted IDs.

Handlers are purely responsible for the final publication of aggregated signals—they contain zero internal logic or filtering.

### Stage C: Atomic Execution (The Listeners)
The project publishes a second, internal event to the `project-aggregated-events` topic. Multiple **Atomic Purist Listeners** subscribe to this topic:
- `ProjectAggregated_AuthUserCountListener`: Refreshes denormalized user counts.
- `ProjectAggregated_TaskCleanupListener`: Purges the `project_task` table.
- `ProjectAggregated_TeamCleanupListener`: Purges the `project_team` table.

## 3. Atomic Purity & Relational Integrity
We follow the **One Listener per Table** principle. Because these listeners run in parallel, we rely on the database's Foreign Key constraints and Kafka's retry mechanism to handle dependencies.

> [!TIP]
> If the `Task` listener runs before the `TaskLink` listener, the DB will block the deletion (FK violation). The `Task` listener will then sleep and retry, eventually succeeding once the `TaskLink` listener has cleared the dependencies.

## 4. High-Performance SQL Pattern
Execution listeners use the `VALUES` join pattern to update or delete thousands of rows in a single database round-trip:

```sql
UPDATE users SET 
    projects_count = users.projects_count + v.delta
FROM (
    SELECT * FROM UNNEST($1::uuid[], $2::int[])
) AS v(id, delta)
WHERE users.id = v.id;
```

## 5. Scaling Benefits
- **IO Density**: Reduced by up to 100x depending on batch size.
- **Stability**: Kafka act as a self-pacing buffer, protecting the database from traffic spikes.
- **Traceability**: naming listeners like `[Topic]_[Action]Listener` ensures the system's event flow is visible in logs.
