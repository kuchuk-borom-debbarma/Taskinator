# 5. Task Deletion Architecture

When deleting tasks in a highly scaling system, we DO NOT rely on the database layer (`ON DELETE CASCADE`) to automatically delete children. 

While database cascades seem convenient, they cause **massive database locking** when a task has thousands of nested sub-tasks. Furthermore, if the database silently deletes the children, our underlying Event-Driven Architecture (EDA) never learns about them, causing other micro-services (like the Trigger Service) to leave behind orphaned data.

To solve this, we removed all `REFERENCES` constraints from our database schema entirely. Relational integrity is enforced completely asynchronously in the application layer.

Here is an easy-to-follow flow of how the asynchronous EDA Deletion Loop works:

## The Deletion Flow

### 1. Initial Parent Deletion
- A client requests the deletion of a Task.
- **REST Layer Action**: We execute a fast, targeted Postgres `DELETE` for **only** that specific Parent task.
- **Publish**: The `TaskServiceImpl` publishes a `PARENT_TASK_DELETED` event holding the deleted task's entity payload (which includes its `materialized_path`).

### 2. The Sweeper Loop (Child Deletions)
The `TaskDeleteListener` acts as a background sweeper for children. 

- **Intercept**: It listens to the `PARENT_TASK_DELETED` event.
- **Chunking**: Using the `materialized_path` from the event payload, it executes a database query to find and securely delete exactly 100 child tasks at a time.
- **Publishing Chunks**: It publishes a `CHILDREN_TASK_DELETED` event with an array of those 100 newly deleted IDs.
- **Re-Queueing for More**: 
   - If there are still children remaining in the database, the listener **republishes** the `PARENT_TASK_DELETED` event to the Kafka broker.
   - Because `eventBus.publish()` internally issues a brand new UUID for the republished event, our Idempotency framework treats the looped payload as a fresh, unhandled message! 
   - The loop continues gracefully yielding to other 10k RPS traffic until zero children remain.

### 3. Asymptotic Sub-Domain Cleanup (Trigger Service)
Other decoupled domains handle their cleanups easily and independently.

- The **Trigger Service** has a `TaskDeletedListener` that listens to **both** `PARENT_TASK_DELETED` and `CHILDREN_TASK_DELETED`.
- Whenever it receives an event, it takes the neat arrays of `taskIds` and executes a simple, performant query to securely drop all linked Triggers (`DELETE FROM project_task_trigger_table WHERE fk_task_id = ANY(taskIds)`).

## Why build it this way?
1. **Zero Lock Escalation**: The database is never locked for exhaustive recursive scans.
2. **Minimal Memory & Network Footprint**: Chunking tasks into groups of 100 prevents Out-Of-Memory application crashes and Kafka payload saturation.
3. **Resilient**: If the server crashes mid-deletion, Kafka will reattempt the event exactly where the 100-chunk sweeper left off.
