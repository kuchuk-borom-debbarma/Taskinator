# Automations

## What Are Automations?

Automations are project-owned reactive rules that respond to events happening within a project's domain — across its tasks, members, and teams — and execute user-defined actions in response.

They are the answer to repetitive, conditional work that humans shouldn't have to do manually. Instead of a team lead manually updating task statuses as work progresses, or a project owner manually notifying members when something changes, automations handle that silently in the background.

An automation watches for something to happen. When it does, and the conditions are right, it acts.

---

## The Mental Model: IF → THEN → CLEANUP

Every automation is a rule with three parts:

```
IF    something happens AND conditions are met

THEN  do one or more actions

CLEANUP  (optional) clean up after yourself
```

This is intentionally simple. There are no branches, no loops, no scripts. An automation is a single flat rule — not a workflow engine.

### IF — The Trigger and Conditions

The **trigger** is the event that wakes an automation up. It is always a domain event from within the project's world:

- Something happened to a **task** (status changed, assigned, linked to another task, completed)
- Something happened to the **project** (a member was added or removed, a team was attached)
- Something happened to a **team** (a member was added or removed)

The **conditions** are optional filters that narrow down when the automation should actually act. A trigger fires the automation, but the conditions decide whether it follows through.

For example:
- Trigger: `task.status_changed`
- Condition: `task.status == "done" AND task.assignee != null`

Without conditions, the automation fires on every matching event. Conditions make it precise.

### THEN — Actions

Actions are what the automation does when the conditions are met. They are global — an automation attached to a project can act on tasks, the project itself, or its teams. There is no artificial restriction on what domain an action can touch.

Examples:
- `UPDATE_TASK` — change a field on a task (status, assignee, priority)
- `NOTIFY` — send an internal notification to a user or role
- `CREATE_TASK` — spawn a new task from a template
- `ADD_MEMBER` — add a user to the project or team
- `REMOVE_MEMBER` — remove a user from the project or team

Multiple actions can be defined. They execute in parallel.

### CLEANUP — Optional Self-Destruction

The cleanup phase handles what happens to the automation or the triggering entity after the actions run. This is separate from actions because it is about the lifecycle of the rule or entity itself — not about the work being done.

Two cleanup options exist:

- **`DELETE_SELF`** — The automation deletes itself after firing. This turns it into a one-shot rule. Useful for onboarding flows, one-time migrations, or any automation that should only ever fire once.
- **`DELETE_TASK`** — The triggering task is deleted after the actions run. Useful for cleanup rules like "when a task has been cancelled for N days, delete it."

Cleanup is optional. Most automations have none.

---

## Where Automations Live

Automations are a **first-class component of a Project**, alongside members, teams, and tasks.

```
Project
  ├── Members
  ├── Teams
  ├── Tasks
  └── Automations
```

There is no global automation registry. Each project manages its own rules independently. An automation is always scoped to exactly one project, and it only ever fires in response to events that originate within that project's domain.

This scoping is a deliberate choice. It keeps automations understandable — you always know which project's rules are running. It prevents one project's automations from unexpectedly affecting another. And it makes deletion clean: when a project is deleted, its automations go with it.

---

## How They Execute

Automations execute **asynchronously via Kafka**. When a domain event fires, it flows through the existing event pipeline. The automation engine consumes it, identifies all enabled automations in that project whose trigger matches, checks each automation's conditions, and dispatches the actions for those that pass.

This means:

- **Zero latency impact on mutations** — the user's action completes immediately. Automations run in the background.
- **Multiple automations run in parallel** — if three automations all match the same event, all three fire concurrently.
- **Actions use rolling state** — before applying a write, an action re-reads the current state of the target entity from the database. It does not act on a frozen snapshot from when the event fired. This ensures actions reflect reality.

---

## Conflict Handling

Because automations run in parallel and use rolling state, two automations could attempt to write the same field on the same entity at the same time. This is handled by two independent guards:

**Optimistic locking** — Every entity carries a version number. An action reads the entity at version N and writes back expecting version N. If another write (from another automation, or from the user) has already incremented it to N+1, the write is rejected and the action is silently discarded.

**The lock flag** — A task can be marked as automation-locked. When the automation engine reaches a locked task, it skips all actions on it entirely. The lock is off by default. A user enables it explicitly to declare: *"I am managing this task manually. Automations should not touch it."*

The rule is simple: **the human always wins**. Automations are advisory. They act when nothing else is in the way.

---

## What Automations Are Not

**They are not a workflow engine.** There are no branches, retries, or multi-step orchestration. If you need a task to wait for an external approval, automations are not the right tool.

**They are not global.** An automation cannot watch events from a different project. There is no cross-project trigger.

**They are not authoritative.** An automation that updates a task's status does not own that status. A user can always override it. The lock flag exists precisely to express that override.

**They do not guarantee exactly-once execution.** They are at-least-once, with idempotency keys preventing duplicate application of the same action from the same event.

---

## Summary

| Property | Value |
|---|---|
| Scope | Per-project |
| Trigger | Domain events (task, project, team) |
| Conditions | Optional field comparisons on trigger entity |
| Actions | Global — can touch tasks, project, teams |
| Execution | Async via Kafka, parallel, rolling state |
| Conflict resolution | Optimistic locking + lock flag |
| Cleanup | `DELETE_SELF` (one-shot) or `DELETE_TASK` |
| Human override | Always wins |
