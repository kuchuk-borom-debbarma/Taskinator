# Automation Traceability

## The Problem

Automations execute asynchronously in the background. From the user's perspective, they fire a mutation, walk away, and things happen. When something unexpected occurs — a task status changed on its own, a member was removed, a notification arrived — there is no obvious trail to follow.

Traceability answers the questions users will always eventually ask:

- *"Why did this automation fire?"*
- *"What did it actually do?"*
- *"Why didn't my automation run?"*
- *"What triggered that chain of events?"*

Without answers, automations become black boxes that erode trust in the system.

---

## The Design: Correlation Chain + Execution Log

Traceability is built from two complementary pieces.

### 1. Correlation IDs on All Events

Every domain event carries three identity fields:

```
event_id        — unique ID for this specific event
correlation_id  — the ID of the root user action that started the chain
causation_id    — the event_id of the immediate parent that caused this event
```

The `correlation_id` never changes as a wave propagates through the graph. It is set once — at the original user action — and every downstream event inherits it.

The `causation_id` changes at each hop. It points to the direct parent event, making it possible to reconstruct the full causal chain step by step.

**Example**: User marks Task A as done.

```
E1  event_id=E1  correlation_id=abc  causation_id=null
    "user marked Task A as done"

E2  event_id=E2  correlation_id=abc  causation_id=E1
    "automation set Task B to ready (caused by E1)"

E3  event_id=E3  correlation_id=abc  causation_id=E2
    "automation notified assignee of Task B (caused by E2)"
```

Query `correlation_id=abc` → the complete trace of everything that happened from a single user click.

---

### 2. Automation Run Log

Every time an automation fires, a run record is written to the `automation_run` table. This is append-only and never mutated.

```
automation_run:
  id
  automation_id        — which automation fired
  automation_snapshot  — JSON snapshot of the rule at time of execution
                         (captures the rule even if it's later edited or deleted)
  correlation_id       — links this run to the full event chain
  causation_event_id   — the specific event that triggered this run
  triggered_at
  status               — "success" | "skipped" | "failed"
  skip_reason          — why the run was skipped (lock, condition failed, etc.)
  conditions_result    — JSON: each condition with its evaluated value and pass/fail
  actions_result       — JSON: each action with its outcome and any error
```

The `automation_snapshot` field is important. It captures the exact rule definition at the time of execution. If a user later edits or deletes the automation, the historical run record still shows exactly what rule fired and why.

## UI Design

The traceability UI has two levels: the **Run History** list for a given automation, and the **Run Detail** view for a single execution.

---

### Run History — Automation Level

This is the first screen users reach when they open an automation's history. It shows a reverse-chronological list of every time the automation fired.

```
┌─────────────────────────────────────────────────────────────────┐
│  Automation: "Set task to ready when all predecessors complete"  │
│                                                          [Edit]  │
├─────────────────────────────────────────────────────────────────┤
│  Run History                                                     │
│                                                                  │
│  ● Success   Task B — 2 min ago              [View run →]        │
│  ● Success   Task F — 14 min ago             [View run →]        │
│  ○ Skipped   Task C — 1 hour ago             [View run →]        │
│  ✕ Failed    Task D — 3 hours ago            [View run →]        │
│  ● Success   Task A — 5 hours ago            [View run →]        │
│                                                                  │
│  Showing 5 of 142 runs        [Load more]                        │
└─────────────────────────────────────────────────────────────────┘
```

**Status indicators:**
- `●` green — automation ran and all actions succeeded
- `○` grey — automation was triggered but skipped (conditions failed or task locked)
- `✕` red — automation ran but one or more actions failed

Each row shows the entity involved (the task, project, or team that was the subject of the triggering event) and the time elapsed. Clicking a row opens the Run Detail view.

---

### Run Detail — Single Execution

This is the diagnostic screen. It is structured as a vertical timeline with three collapsible sections: Trigger, Conditions, and Actions.

```
┌─────────────────────────────────────────────────────────────────┐
│  ← Back to Run History                                           │
│                                                                  │
│  Run · 2 min ago · ● Success                                     │
│  Triggered by: task.status_changed on "Implement auth module"    │
│                                                                  │
│  ┌─ TRIGGER ───────────────────────────────────────────────────┐ │
│  │  Event: task.status_changed                                  │ │
│  │  Entity: Task "Implement auth module"                        │ │
│  │  Changed: status "in_progress" → "done"                     │ │
│  │  Actor: Sarah (user action)                                  │ │
│  │  Correlation ID: abc-123   [View full chain ↗]               │ │
│  └─────────────────────────────────────────────────────────────┘ │
│                                                                  │
│  ┌─ CONDITIONS ────────────────────────────────────────────────┐ │
│  │  ✓  task.status == "done"          evaluated: "done"        │ │
│  │  ✓  task.predecessor_count == 0    evaluated: 0             │ │
│  └─────────────────────────────────────────────────────────────┘ │
│                                                                  │
│  ┌─ ACTIONS ───────────────────────────────────────────────────┐ │
│  │  1. UPDATE_TASK                                    ● Done   │ │
│  │     target: Task "Design review"                            │ │
│  │     field: status → "ready"                                 │ │
│  │                                                             │ │
│  │  2. NOTIFY                                         ● Done   │ │
│  │     target: assignee of Task "Design review"                │ │
│  │     message: "Your task is now unblocked"                   │ │
│  └─────────────────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────────────────┘
```

**Key design decisions:**

- **Conditions always show their evaluated value**, not just pass/fail. A user should be able to read "task.predecessor_count == 0 evaluated: 0" and immediately understand why it passed.
- **Skipped runs explain why they were skipped.** If conditions failed, the failing condition is highlighted in red with its actual evaluated value. If the task was locked, a banner reads: "This task has automation locked. No actions were applied."
- **The Correlation ID is a clickable link** that opens the full causal chain view.

---

### Causal Chain View

Accessible from the "View full chain" link in any run detail. Shows the complete tree of events and automation runs that share the same `correlation_id`.

```
Root event (user action)
  Sarah marked Task A as done

  ├── Automation fired: "Set successors to ready"
  │   └── Updated Task B → ready
  │
  │       ├── Automation fired: "Set successors to ready"
  │       │   └── Updated Task C → ready
  │       │
  │       └── Automation fired: "Notify assignee on ready"
  │           └── Notified: james@example.com
  │
  └── Automation fired: "Notify assignee on ready"
      └── Notified: sarah@example.com
```

This view makes wave propagation visible and legible. A user can see exactly how far a single action rippled through the graph.

## Why Not Event Sourcing or WAL?

**Event sourcing** stores every state change as an immutable event, and derives current state by replaying the log. It is a complete architectural paradigm. Introducing it only for automation traceability would mean rebuilding the domain's persistence model. The cost is not justified.

**WAL (Write-Ahead Log / logical replication)** captures every database write at the infrastructure level via tools like Debezium. It gives you raw diffs — not semantic meaning. A WAL entry says "column `status` on row `x` changed from `in_progress` to `done`." It does not say "Automation Y ran because Condition Z passed." You would need to reconstruct the semantic layer on top of raw WAL anyway.

The `automation_run` table is purpose-built. It stores exactly the information users need to understand what happened and why — nothing more.

---

## Summary

| Mechanism | Purpose |
|---|---|
| `correlation_id` on events | Links every event in a causal chain back to the root user action |
| `causation_id` on events | Identifies the immediate parent event at each hop |
| `automation_run` table | Append-only log of every automation execution |
| `automation_snapshot` field | Preserves rule definition at time of execution |
| Run History UI | Reverse-chronological list of runs for an automation |
| Run Detail UI | Full diagnostic view: trigger → conditions → actions |
| Causal Chain UI | Visual tree of the full event propagation from the root user action |
