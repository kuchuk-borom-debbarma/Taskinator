# 20. Chunked Self-Signaling Deletion Architecture

## 1. Problem Statement

Taskinator's task deletion flow involves cascading cleanup across three heavyweight tables:

| Table | Reason for cleanup |
|---|---|
| `project_task` | The task record itself |
| `task_link` | Dependency edges involving the deleted task |
| `task_reachability` | Closure table rows (ancestor/descendant pairs) |

Before this refactor, every listener performed an **unbounded bulk DELETE** inside a single transaction:

```sql
DELETE FROM project_task WHERE fk_project_id = ANY($projectIds)
```

### Why this is dangerous

A single project can have tens of thousands of tasks. A single unbounded DELETE on `project_task`, `task_link`, or `task_reachability` will:

1. **Hold an exclusive row lock** on every matched row for the duration of the transaction. PostgreSQL's MVCC does not release row locks until commit — meaning all concurrent readers and writers to those rows are blocked.
2. **Block the reachability repair CTE**, which is a cross-join on surviving rows. Running the repair inside the same transaction as the deletion forces both the lock window and the expensive graph rebuild to overlap.
3. **Scale super-linearly** with data volume. A project with 50k tasks requires locking 50k rows simultaneously, generating a huge lock table entry and increasing the chance of deadlocks with concurrent writers.

At the 10k RPS target, these stop-the-world deletes would cause cascading timeout failures.

---

## 2. Solution: Chunked Self-Signaling Loop

The core insight is to replace one unbounded transaction with a **recursive chain of bounded transactions**, each processing at most `BULK_DELETE_CHUNK_SIZE = 2,000` rows.

Each iteration of the loop:
1. Opens a short-lived transaction.
2. Deletes up to 2,000 rows.
3. **Atomically** writes a continuation signal to the `outbox_events` table before the transaction commits.
4. Commits — releasing all row locks.
5. The Outbox Relay picks up the continuation signal and triggers the next iteration.

This is called **self-signaling** because the listener schedules its own next invocation from within the same transaction that performs the deletion. There is no external orchestrator; the loop is driven entirely by the outbox.

### Visual: Single-pass vs. Chunked

```
BEFORE (single pass):
┌────────────────────────────────────────────────────────────┐
│ TXN: DELETE 50,000 rows (holds exclusive locks for ~2s)    │
│       + repair CTE (another expensive cross-join)          │
└────────────────────────────────────────────────────────────┘

AFTER (chunked self-signaling):
┌─────────────────┐  ┌─────────────────┐  ┌─────────────────┐
│ TXN 1           │  │ TXN 2           │  │ TXN N (final)   │
│ DELETE 2,000    │→ │ DELETE 2,000    │→ │ DELETE < 2,000  │
│ + OUTBOX signal │  │ + OUTBOX signal │  │ + REPAIR CTE    │
│ commit (~10ms)  │  │ commit (~10ms)  │  │ commit          │
└─────────────────┘  └─────────────────┘  └─────────────────┘
         ↑ loop driven by Outbox Relay (LISTEN/NOTIFY)
```

## 3. Event Flow Anatomy

### 3.1 Project Deletion Flow

When a project is deleted, the Project Aggregator emits three parallel cleanup signals:

```
project.deleted
    ├── DELETE_PROJECT_TASK              → ProjectAggregated_DeleteProjectTask
    ├── DELETE_PROJECT_TASK_LINK         → ProjectAggregated_DeleteProjectTaskLink
    └── DELETE_PROJECT_TASK_REACHABILITY → ProjectAggregated_DeleteProjectReachability
```

Each of these operates independently on its own table in its own chunked loop.

```
DELETE_PROJECT_TASK
  ↓ (chunk 1: 2,000 rows deleted)
DELETE_PROJECT_TASK_CHUNK          ← self-signal written to outbox atomically
  ↓ (chunk 2: 2,000 rows deleted)
DELETE_PROJECT_TASK_CHUNK
  ...
  ↓ (final chunk: < 2,000 rows deleted)
  [loop terminates — no continuation signal emitted]
```

### 3.2 Task Deletion Flow (Reachability with Deferred Repair)

When individual tasks are deleted (not a whole project), the flow is:

```
task.deleted
  ↓
DELETE_TASK_REACHABILITY           → TaskAggregated_DeleteTaskReachabilityListener
  ↓ (chunk 1: 2,000 rows deleted)
DELETE_TASK_REACHABILITY_CHUNK     ← self-signal
  ↓ ...
  ↓ (final chunk: < 2,000 rows deleted)
  repairTaskReachabilityForProjects(affectedProjectIds)  ← runs exactly ONCE
```

The critical difference here is the **deferred repair strategy** (see §5).

## 4. Loop Termination Condition

Every listener uses the same deterministic termination condition:

```typescript
if (affectedCount === BULK_DELETE_CHUNK_SIZE) {
    // Chunk was full → rows likely remain → emit continuation signal
    await appendEventsToOutbox(trx, [ { type: DELETE_*_CHUNK, ... } ]);
} else {
    // Chunk was not full → this was the final pass → loop terminates
}
```

**Why this is correct**: A chunk is "full" if and only if exactly `BULK_DELETE_CHUNK_SIZE` rows were deleted. If fewer rows were deleted, the `LIMIT` was not reached, which proves no more rows matching the filter exist. The loop is provably finite for any bounded table.

**Edge case — zero rows**: If the initial signal arrives for a project with no tasks (e.g., a freshly created project that was immediately deleted), `affectedCount = 0 < BULK_DELETE_CHUNK_SIZE`, and the loop terminates immediately on the first pass. No phantom signals are ever emitted.

## 5. Deferred Repair Strategy for the Closure Table

The `task_reachability` (closure table) requires a repair step after rows are purged, to rebuild the transitive paths that survived the deletion. This repair uses a recursive CTE:

```sql
-- Simplified: full rebuild from surviving task_link rows
WITH RECURSIVE reachable AS (
    SELECT source_task_id AS ancestor_task_id,
           target_task_id AS descendant_task_id,
           fk_project_id, 1 AS depth
    FROM task_link WHERE fk_project_id = ANY($projectIds)
    UNION ALL
    SELECT r.ancestor_task_id, tl.target_task_id, tl.fk_project_id, r.depth + 1
    FROM reachable r
    JOIN task_link tl ON tl.source_task_id = r.descendant_task_id
                      AND tl.fk_project_id = r.fk_project_id
)
INSERT INTO task_reachability ...
ON CONFLICT DO NOTHING;
```

### Why defer?

If we ran this repair after **every chunk**, we would:

- Execute N expensive recursive CTEs (one per chunk), where N = ⌈total_rows / 2000⌉.
- Run the repair on a **partially purged** closure table, meaning many of the rebuilt paths would be immediately invalidated by the next chunk's deletion.
- Hold write locks on `task_reachability` during each repair, blocking concurrent reads.

By deferring to the **final chunk only**, we:

- Run the repair exactly **once**, on the fully-purged table.
- Guarantee the rebuilt paths are correct because no further deletions will follow.
- Minimize total lock time on `task_reachability`.

### Project-Scoped Repair

The repair is scoped to only the projects whose `task_reachability` rows were touched:

```typescript
const { affectedCount, affectedProjectIds } =
    await deleteTaskReachabilityChunk(trx, taskIds);

// Only on the final chunk:
await repairTaskReachabilityForProjects(trx, affectedProjectIds);
```

`affectedProjectIds` is derived from `RETURNING fk_project_id` in the DELETE statement. This means the repair CTE is scoped with a `WHERE fk_project_id = ANY($affectedProjectIds)` filter, avoiding a full-table scan on projects that weren't affected.

## 6. `ctid`-Based Chunking

`task_reachability` has a **composite primary key** `(fk_project_id, ancestor_task_id, descendant_task_id)` with no surrogate `id` column. The standard chunking pattern — `WHERE id IN (SELECT id FROM ... LIMIT N)` — does not apply.

The solution uses PostgreSQL's **`ctid`** (physical tuple identifier):

```sql
DELETE FROM task_reachability
WHERE ctid IN (
    SELECT ctid FROM task_reachability
    WHERE fk_project_id = ANY($projectIds)
    LIMIT 2000
)
RETURNING fk_project_id
```

**Why `ctid` is safe here**: `ctid` is a physical row address. It is stable within a single SQL statement — the subquery and the outer DELETE execute as one atomic operation, so the `ctid` values returned by the subquery are guaranteed to refer to the same rows that the DELETE touches. `ctid` can change between statements (e.g., after `VACUUM FULL`), but that is irrelevant because we never store it across transaction boundaries.

Tables with a surrogate `id` column (`project_task`, `task_link`) use the standard pattern instead:

```sql
DELETE FROM project_task
WHERE id IN (
    SELECT id FROM project_task
    WHERE fk_project_id = ANY($projectIds)
    LIMIT 2000
)
RETURNING id
```

## 7. Idempotency

Every listener uses `claimEventsAtomic` to perform an **explicit idempotency claim** at the start of each transaction:

```typescript
const unprocessed = await claimEventsAtomic(
    trx,
    events,
    'task-decommissioning-group',
);
if (unprocessed.length === 0) return;
```

This inserts a claim record into an `idempotency_claims` table using `ON CONFLICT DO NOTHING` inside the same transaction. If two consumers race to process the same event (e.g., after a failover), only one will successfully insert the claim — the other will get back an empty `unprocessed` array and exit cleanly.

This is especially important for self-signaling continuation events. Because the continuation signal is written atomically in the same transaction as the chunk deletion, a crash-and-replay scenario will re-deliver the same continuation event. The idempotency claim ensures the chunk is not deleted twice.

---

## 8. Outbox Integration

Continuation signals are written via `appendEventsToOutbox` inside the same transaction as the DELETE:

```typescript
await appendEventsToOutbox(trx, [{
    kafka_topic: KAFKA_TOPICS.PROJECT_AGGREGATED,
    payload: {
        type: KAFKA_EVENTS.PROJECT_AGGREGATED.DELETE_PROJECT_TASK_CHUNK,
        projectIds,
    },
}]);
```

This is **not a best-effort fire-and-forget**. The continuation event only exists if the transaction commits. If the transaction rolls back (e.g., due to a connection loss mid-delete), the continuation signal is also rolled back — meaning the loop will not advance, and the rows that were not deleted will remain. This is safe: the initial trigger event is still present in the outbox (it has not been deleted), so the loop will be restarted from the beginning by the Outbox Relay on the next poll cycle.

### Why `appendEventsToOutbox` and not direct publish?

Direct publishing to the in-memory event bus would bypass the Outbox's durability guarantee. If the process crashes after the DELETE commits but before the in-memory publish, the continuation is lost and cleanup stalls indefinitely. Writing to `outbox_events` inside the transaction makes the continuation signal **durable at the same moment the data mutation is committed**.

## 9. Chunk Size Tuning

The chunk size is defined as a single constant:

```typescript
// src/modules/task/internal/TaskQueries.ts
export const BULK_DELETE_CHUNK_SIZE = 2_000;
```

**Choosing 2,000**: At a typical row size of ~200 bytes for `project_task`, 2,000 rows = ~400 KB of locked data per transaction. At a write throughput of 10k RPS, this keeps individual deletion transactions under 15ms on standard hardware, well within acceptable lock contention windows.

**Tuning guidance**:

| Symptom | Action |
|---|---|
| Deletion transactions timing out | Decrease chunk size |
| Deletion loop taking too long for large projects | Increase chunk size |
| Deadlocks on `task_reachability` | Decrease chunk size |

Change only `BULK_DELETE_CHUNK_SIZE`. All four listeners and both chunked query functions read from this constant — no other code needs to change.

## 11. Key Invariants

1. **Continuation signals are internal only.** The `*_CHUNK` event types are never emitted by external producers (the aggregator, API layer, etc.). Only the listener itself can emit them, from within a delete transaction.

2. **The repair CTE runs exactly once per deletion sequence**, on the final chunk, after all stale rows have been purged.

3. **The loop is always finite.** Each chunk deletes strictly fewer than or equal to `BULK_DELETE_CHUNK_SIZE` rows. Because the table is finite and rows are never re-inserted during a deletion sequence, the loop converges.

4. **No lock escalation.** Each transaction holds at most `BULK_DELETE_CHUNK_SIZE` row locks. PostgreSQL never escalates to table locks at this scale.

5. **Idempotency is unconditional.** Even continuation signals go through `claimEventsAtomic`. A re-delivered continuation event from a crash-recovery scenario is silently skipped.
