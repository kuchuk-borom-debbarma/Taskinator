# 7. Task Triggers Architecture

Taskinator-v2 uses an **Event-Driven Automation (EDA)** system to handle task lifecycles, dependencies, and external integrations. This system is decoupled from the core Task Service to ensure high performance (10k RPS optimization) and reliability.

## Trigger Types

### 1. SEQUENCE_UNLOCK (Dependency Management)
- **Purpose**: Automates sequential workflows where Task B depends on Task A.
- **Placement**: Must be placed on **Task A** (the blocker).
- **Behavior**: When Task A's status is updated to `DONE`, the trigger automatically updates Task B's status to `TODO` (or a custom status).
- **Data**: 
  - `targetTaskId`: UUID of the task to unlock.
  - `targetStatusToSet`: (Optional) Default is `TODO`.

### 2. BLOCK_PARENT_DONE (Guard)
- **Purpose**: Ensures project integrity by preventing "Done" parent tasks from having "Incomplete" children.
- **Placement**: Must be placed on the **Parent Task**.
- **Behavior**: If the Parent is marked `DONE`, the trigger counts its children. If any child is not `DONE`, the trigger automatically reverts the Parent's status to `IN_PROGRESS` (or a custom status).
- **Data**:
  - `revertStatusTo`: (Optional) Default is `IN_PROGRESS`.

### 3. WEBHOOK (External Integration)
- **Purpose**: Connects Taskinator to external services (Slack, Discord, custom APIs).
- **Placement**: Any task.
- **Behavior**: Whenever the task is updated, the trigger sends a POST request with the full task state and update context to a specified URL.
- **Data**:
  - `url`: The target endpoint.
  - `secret`: (Optional) Sent in the `X-Taskinator-Signature` header for verification.

## Backend Implementation

The system follows a **Detect → Delegate → Process** lifecycle:

### Phase 1: Detection (`ProjectTaskUpdatedListener`)
- Listens for the `PROJECT_TASK.UPDATED` Kafka event.
- **Safety**: Skips any updates initiated by the `SYSTEM` user to prevent infinite recursion/event storms.
- Queries `project_task_trigger_table` for all automations linked to the updated `taskId`.
- Publishes a `PROJECT_TASK_TRIGGER.TRIGGER` event for every automation found.

### Phase 2: Delegation (`TaskTriggerListener`)
- Acts as a dispatcher. It receives the trigger event and routes it to the specific processor based on the `triggerType`.

### Phase 3: Processing (`Trigger Engine`)
- Processors execute the business logic (e.g., counting children or sending HTTP requests).
- **Atomic Corrective Actions**: If a processor needs to change a task status (like a Guard reverting a Parent), it uses a **PostgreSQL wCTE** (Writeable Common Table Expression). 
  - It updates the task and inserts a new event into the `outbox_events` table in a single atomic transaction.
  - This ensures that "Corrective Updates" are also broadcast to the rest of the system.

## Technical Edge Cases
- **Recursive Triggers**: Because the Trigger Engine emits standard `updated` events (via the Outbox), triggers can chain. Task A unlocks B, which triggers a webhook on B.
- **Idempotency**: All trigger consumers use the `processed_event` table to ensure that a single Kafka message never executes a trigger twice, even during network retries.
