# Plan 42-01: Consumer & Service Runtime Wiring

## Objective

Wire task domain events into auto-action rule lookup and execution through a thin consumer and simple auto-action service functions. Keep internal engines hidden and avoid coupling consumers to queries.

## Requirements Covered

- **RUNTIME-01**: Auto-action consumer can receive supported domain events and route them to the auto-action service.
- **RUNTIME-02**: Auto-action service can find eligible rules for an event without coupling the consumer to internal query details.
- **RUNTIME-03**: Auto-action service can trigger rule execution using existing context, condition, and action orchestration.
- **RUNTIME-04**: Consumer handling preserves idempotency, trace/depth metadata, and failure visibility.
- **SVC-01**: Auto-action module exposes service functions needed by consumers without leaking internal engines.
- **SVC-02**: New service functions stay small, readable, and single-purpose.

## Constraints

- Keep code modular, simple, loosely coupled, and easy to follow.
- SOLID where useful; KISS always.
- Consumer must not import internal queries or engines.
- Service implementation may use internal queries and executor.
- Query functions remain in `auto-action/internal/queries`.
- No GraphQL work in this phase.

## Tasks

### Task 1: Add Runtime Query & Executor Boundary

**Goal:** Remove direct DB access from pipeline execution and add query support for trigger lookup.

Steps:
1. Add query function to fetch an auto action for execution by ID.
2. Update `executeAutoActionPipeline` to call the query function instead of importing `db`.
3. Add query function for active project auto-actions that are eligible for trigger filtering.
4. Keep trigger filtering in service if JSON trigger shape is easier to handle in TypeScript.
5. Add/adjust focused tests proving executor still skips inactive rules and executes active pipelines.

Acceptance:
- `internal/execution/executor.ts` no longer imports `db`.
- Query logic lives in `AutoActionQueries.ts`.
- Existing auto-action tests still pass or are updated with focused mocks.

### Task 2: Add Service Runtime Trigger Functions

**Goal:** Service owns event-to-rule orchestration.

Steps:
1. Extend `AutoActionService` with a task-event handling method, e.g. `handleTaskEvents(events: DomainEvent[]): Promise<void>`.
2. In `AutoActionServiceImpl`, normalize supported task events (`task.created`, `task.updated`; include delete only if existing trigger/schema supports it cleanly).
3. Derive `projectId`, `taskId`, `actorId`, `traceId`, and `wasSnapshot` from event data.
4. Select active auto actions for `EntityScope.TASK` and trigger type.
5. Execute each matching pipeline via existing `executePipeline`/executor path.
6. Log skipped malformed or unsupported events; throw real execution failures so consumer visibility remains intact.

Acceptance:
- Runtime trigger orchestration is behind `AutoActionService`.
- Service methods are small enough to read without spelunking.
- No consumer-level query/engine coupling is needed.

### Task 3: Add Auto Action Consumer & Registry Wiring

**Goal:** Runtime event bus calls auto-action service when task events fire.

Steps:
1. Create `AutoActionTaskEventConsumer` under `modules/auto-action/internal/listeners/`.
2. Subscribe to `KAFKA_TOPICS.TASK` with a dedicated group such as `auto-action-task-trigger-group`.
3. Register handlers for supported task events.
4. Delegate batch events to `autoActionService.handleTaskEvents(events)`.
5. Register the consumer in `kafka/registry.ts`.
6. Add focused unit test for consumer delegation using mocked `eventBus` and `autoActionService`.

Acceptance:
- Consumer initializes from global Kafka registry.
- Consumer is thin: subscribe + delegate only.
- Test verifies topic, group, event handlers, batch mode, and service call.
