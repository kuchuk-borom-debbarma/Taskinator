# Architecture Patterns

**Domain:** Event-Driven Task Automation
**Researched:** Today

## Recommended Architecture

The system should follow an **Event-Condition-Action (ECA)** pattern built on top of a **Message Broker/Event Bus**. This provides the necessary decoupling to treat automated actions indistinguishably from user actions. 

Instead of hardcoded "if status == done then... " logic within the task mutation API, the system uses a reactive, push-based model.

### Component Boundaries

| Component | Responsibility | Communicates With |
|-----------|---------------|-------------------|
| **Task Engine (Producer)** | Handles CRUD operations for tasks. Emits standardized domain events (e.g., `task.updated`, `task.created`) upon successful mutation. | Database (Write), Event Bus (Publish) |
| **Event Bus (Broker)** | Central nervous system. Routes events from producers to interested consumers. Ensures delivery and decoupling. | Task Engine, Automation Engine |
| **Automation Engine (Condition)** | Subscribes to task events. Fetches workspace-specific rules. Evaluates event payloads against configured conditions (the "Rule Engine"). | Event Bus (Subscribe), Database (Read rules), Action Queue (Publish) |
| **Action Dispatcher / Queue** | Buffers validated actions to be executed. Ensures retries and prevents the Automation Engine from blocking during execution. | Automation Engine, Action Workers |
| **Action Workers (Consumer)** | Executes the actual automation (e.g., reassigning a task, sending a webhook). Crucially, these often call the Task Engine API to perform mutations, acting just like a human user. | Action Queue, Task Engine API, External APIs |

### Data Flow

1. **Trigger:** User updates a task via the UI/API (Task Engine).
2. **Commit & Emit:** Task Engine updates the database and immediately pushes a `task.updated` event to the Event Bus.
3. **Routing & Evaluation:** 
   - The Automation Engine consumes the event.
   - It retrieves active automation rules for the specific workspace.
   - It evaluates the event payload against the rule's conditions (e.g., `if event.changes.status == 'Done'`).
4. **Dispatch:** If conditions match, the Automation Engine constructs an action payload and pushes it to the Action Queue.
5. **Execution:** Action Workers pull from the queue and perform the designated task (e.g., calling the Task Engine to update a related task's status).

## Patterns to Follow

### Pattern 1: Event Sourcing & Standardized Payloads
**What:** Define a strict schema for events containing both the `before` and `after` state of the mutated entity.
**When:** Universal across all producers.
**Example:**
```typescript
{
  "eventId": "evt_123",
  "eventType": "task.updated",
  "workspaceId": "ws_abc",
  "payload": {
     "taskId": "task_789",
     "changes": { "status": { "old": "Todo", "new": "Done" } }
  }
}
```

### Pattern 2: Idempotent Action Workers
**What:** Ensure that if an action worker processes the same message twice (e.g., due to a network retry), the end result is the same.
**When:** Designing any worker that mutates state or calls external APIs.

## Anti-Patterns to Avoid

### Anti-Pattern 1: Synchronous Webhook/Action Execution
**What:** The Task Engine mutates a task and synchronously calls an external API or evaluates complex rules before returning the HTTP response to the user.
**Why bad:** Creates massive latency, couples the core system to external reliability, and makes the UI feel slow. 
**Instead:** Fire-and-forget. Emit an event to the bus and immediately return `200 OK` to the user.

### Anti-Pattern 2: Infinite Automation Loops
**What:** Worker updates a task -> Emits event -> Triggers same rule -> Worker updates task...
**Why bad:** Causes system crashes, massive database loads, and queue flooding.
**Instead:** Include a `source` or `triggeringActor` field in the event payload (e.g., `actor: 'system-automation'`). Allow rules to explicitly ignore events generated by automations.

## Scalability Considerations

| Concern | At 100 users | At 10K users | At 1M users |
|---------|--------------|--------------|-------------|
| **Event Bus** | In-memory Node.js EventEmitter or Redis Pub/Sub | Dedicated Redis Streams or RabbitMQ | Apache Kafka or AWS EventBridge |
| **Workers** | Run in the same process as the API | Separated worker nodes pulling from a queue | Auto-scaling worker clusters based on queue depth |

## Suggested Build Order (Phase Implications)

Based on this architecture, the roadmap should phase the build as follows:
1. **Phase 1: Foundation:** Standardize the event payload and implement a basic Event Bus. Instrument the Task Engine to emit these events.
2. **Phase 2: The ECA Engine:** Build the Automation Engine to consume events and evaluate conditions based on hardcoded/mocked rules.
3. **Phase 3: Action Execution:** Implement the Action Queue and idempotent Workers.
4. **Phase 4: Configurable Workspaces:** Build the UI and database schema for users to dynamically create rules (the "Configurable behavior").
