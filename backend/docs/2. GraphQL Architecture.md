# GraphQL Architecture & Federation

Taskinator uses **Apollo Federation 2.0** to provide a unified API while maintaining a decoupled, microservice-based backend. This allows different teams to own different parts of the data graph without creating a monolithic bottleneck.

## 1. The Topology

Our graph is composed of **Subgraphs** and a single **Gateway**.

### The Gateway (`backend/services/gateway`)
*   **Role:** The entry point for all frontend requests.
*   **Tech:** Node.js (Bun) + Apollo Gateway.
*   **Responsibility:** 
    *   Schema Composition: Fetches schemas from all subgraphs and merges them into a "Supergraph".
    *   Query Planning: Breaks down a single client query into multiple sub-queries for the relevant services.
    *   Auth Forwarding: Passes the `Authorization` header down to subgraphs for identity verification.

### Identity Subgraph (`backend/services/identity`)
*   **Role:** The source of truth for Users.
*   **Tech:** Cloudflare Workers (Bun/Hono) + GraphQL Yoga.
*   **Responsibility:** Owns the `User` entity and profile data (`username`, `email`, `displayName`).

### Workspace Subgraph (`backend/services/workspace`)
*   **Role:** Manages the structural hierarchy of work.
*   **Tech:** Spring Boot + Netflix DGS (Kotlin).
*   **Responsibility:** Extends the `User` entity to add `projects` and `teams`. Owns `Project` and `Team` types.

## 2. Key Patterns & Directives

### Entity Extension
We use the `@key` directive to allow entities to be shared across services.

**In Identity Service:**
```graphql
type User @key(fields: "id") {
  id: ID!
  username: String!
}
```

**In Workspace Service (Extension):**
```graphql
type User @key(fields: "id") @extends {
  id: ID! @external
  projects: [Project!]! # Adds projects to the User type
}
```

### Data Fetching Flow
1.  **Client** requests: `me { username projects { name } }`.
2.  **Gateway** identifies that `username` is in **Identity** and `projects` is in **Workspace**.
3.  **Gateway** calls Identity for the `User` record.
4.  **Gateway** uses the `User.id` from the result to call Workspace's `_entities` resolver to fetch the `projects`.
5.  **Gateway** merges the results into one JSON response.

## 3. Development Workflow

### Adding a New Type
1.  Define the type in the relevant service's `.graphql` file.
2.  If the type should be accessible from another service, add a `@key`.
3.  If you are using the **Workspace Service**, run `./gradlew generateJava` to update the Kotlin types.

### Updating the Gateway
The Gateway uses **Introspection** in development mode. If you change a schema in a subgraph:
1.  Restart the Subgraph.
2.  The Gateway will automatically pick up the changes if it is running in `--watch` mode.

---

## 4. Security
*   **Authentication:** Handled at the Identity service level. The Gateway forwards JWTs.
*   **Authorization:** Subgraphs are responsible for verifying if the `User` (from the forwarded JWT) has permission to access the specific records (e.g., "Does this user own this project?").
