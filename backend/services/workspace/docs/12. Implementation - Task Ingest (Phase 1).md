# 12. Implementation - Task Ingest (Phase 1)

This document provides a detailed technical breakdown of the "Ingest" phase implemented in the Taskinator Workspace service. This phase moves the system from a synchronous, blocking database write model to a high-scale, asynchronous event-driven model.

## 1. The New Request Lifecycle

When a user calls the `createTask` mutation, the following execution path is taken:

1.  **Context Extraction**: The API extracts the `X-User-Id` from the request header.
2.  **ID Generation (ID-First)**: The API generates a **UUID v7** for the Task. This allows the API to tell the client the ID of their task before it ever touches the database.
3.  **Idempotency Generation**: A second unique key is generated to serve as the "Fingerprint" for this specific request.
4.  **Event Production**: A `TaskCreated` event is constructed and pushed to the `workspace-activity` Kafka topic.
5.  **Immediate Response**: The API returns a `PENDING` task object to the client. Total latency: **~5-10ms** (vs. ~50-100ms for a synchronous DB write).

## 2. Component Deep-Dive

### A. The Event Schema (`Events.kt`)
We use a **Sealed Class** to represent different task intents. This ensures type safety and allows the Kafka Consumer to use a single "Unified Entity Stream."

*   **Partitioning Key**: We use the `projectId` as the Kafka key. 
    *   *Result:* All events for "Project A" are processed by the same worker in the exact order they were sent.
*   **Idempotency Key**: Included in every event to prevent "Ghost Tasks" if the network retries or the worker restarts mid-batch.

### B. The Producer Logic (`TaskMutationFetcher.kt`)
The fetcher now acts as a **Traffic Controller** rather than a database client.

```kotlin
// Example of the implemented logic
val taskId = UuidCreator.getTimeOrderedWithRandom().toString()
val idempotencyKey = UuidCreator.getTimeOrderedWithRandom().toString()

val event = TaskEvent.TaskCreated(
    taskId = taskId,
    projectId = input.projectId,
    userId = userId,
    title = input.title,
    idempotencyKey = idempotencyKey
)

kafkaTemplate.send("workspace-activity", input.projectId, event)
```

### C. Kafka Configuration (`application.yaml`)
To support 1M RPS, the producer is tuned for high throughput and high reliability:
*   **`acks: all`**: Ensures the event is replicated across 3 brokers before the API continues.
*   **`enable.idempotence: true`**: The Kafka broker will automatically discard duplicate messages sent by the API if a network retry occurs.
*   **`linger.ms: 10`**: The API will wait up to 10ms to group small requests into a single network packet, significantly reducing CPU overhead.
*   **`compression.type: lz4`**: Compresses the JSON payload to save network bandwidth with minimal CPU cost.

## 3. The Testing Infrastructure

Since we moved to an event-driven model, we updated the test suite to ensure "Build Stability":

1.  **MockitoBean (Spring Boot 4.0.2)**: We use `@MockitoBean` to inject a "Mock" `KafkaTemplate`. This allows the tests to run without a real Kafka broker.
2.  **Shared Test Postgres**: We moved the embedded database logic to `TestPostgresConfiguration.kt`. This ensures that even "Context Load" tests (like `WorkspaceApplicationTests`) have a valid database to talk to.
3.  **Validation**: Our tests still verify the **Domain Logic** (the "what") while mocking the **Infrastructure** (the "how").
