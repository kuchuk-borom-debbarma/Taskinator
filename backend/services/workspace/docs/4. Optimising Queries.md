# Engineering Deep Dive: Optimising Queries for 10k RPS

This document records the evolution of our query design, the "bottleneck" problems we identified, and the specific patterns used to achieve high throughput and low latency.

---

## 1. The "Round-Trip" Problem (Chatty Code)

### The Thought Process
Every time the application talks to the database, there is a cost: Network latency (1-2ms), connection pooling overhead, and database CPU cycles. At 10,000 requests per second, we cannot afford "Chatty" code (multiple calls per request).

### Optimization: SQL `RETURNING *`
**Pattern:** We used `insert { ... }.resultedValues?.singleOrNull()`.
*   **Consistency:** By sourcing `now()` and `version=0` from the application, the returned object matches the database state exactly.
*   **Result:** The database performs the write and returns the full record in **one single statement**.
*   **Win:** 50% reduction in network round-trips for every creation request.

---

## 2. Atomic Data Integrity (The Deletion Order)

### The Thought Process
When using a **Closure Table**, deleting a team involves two tables (`ProjectTeams` and `ProjectTeamClosure`). If the team record delete fails (due to an optimistic lock conflict) but the hierarchy was already deleted, we create a "Zombie Team"—a record that exists but is invisible to tree-traversals.

### Optimization: Succes-First Deletion
**Pattern:** 
1.  `val deletedRows = ProjectTeams.deleteWhere { ... version eq current }`
2.  `if (deletedRows > 0) { ProjectTeamClosure.deleteWhere { ... } }`
**Win:** The system is "Self-Healing." No structural data is touched unless the primary record deletion is confirmed.

---

## 3. Mass Membership Logic (Validated Batching)

### The Thought Process
Adding 100 members to a team requires verifying they belong to the parent project first. Doing this in Kotlin requires fetching large lists into memory.

### Optimization: 2-Call Sweep
**The Pattern:** 
1. **Query 1 (Validation):** `SELECT memberId, name FROM ProjectMembers WHERE projectId = ? AND memberId IN (?)`. This filters valid IDs in the database.
2. **Query 2 (Batch Write):** `ProjectTeamMembers.batchInsert(validatedList)`.
**Win:** We only send and receive the minimal data needed. By using `batchInsert` with `reWriteBatchedInserts=true`, 100 inserts are collapsed into one SQL string.

---

## 4. Hierarchical Data (The "Tax" Mindset)

### The Thought Process
Hierarchies (Teams/Sub-teams) are usually queried using `WITH RECURSIVE`. This is a database killer at scale.

### Optimization: The Closure Table
We decided to **"Pay a tax at Write-time"** to make **"Reads essentially free."**
*   **The Write Tax:** When a team is created, we insert multiple rows into `ProjectTeamClosure` representing every path from root to that team.
*   **The Read Win:** To find "all descendants," we run a simple, indexed B-Tree lookup.
**Performance:** O(1) traversal complexity.

---

## 5. Stability vs. Latency (The Sync/Async Split)

### The Thought Process
The Closure Table "Write Tax" can be slow for very deep trees.

### Optimization: Event-Driven Hierarchy
We split the operation:
1. **Synchronous (Critical):** Create the Team record + Depth 0 (Self) entry. The team is now "real" and visible.
2. **Asynchronous (Heavy):** Fire an event. A background worker calculates the ancestral paths.
**Win:** The user gets a response in < 50ms, while the database handles the heavy math in the background.

---

## 6. UI Consistency: Deterministic Pagination

### The Thought Process
High-frequency writes can cause items with identical timestamps to "jump" between pages during scroll.

### Optimization: The ID Tie-Breaker
**The Pattern:** 
Every paginated query now ends with `.orderBy(Column, SortOrder).orderBy(Table.id, SortOrder.ASC)`.
**Win:** Because IDs are unique, the sort order is now 100% stable. Pagination will never skip or double-count an item.

---

## 8. The CTE Power-Play (Atomic Multi-Table Writes)



### The Thought Process

Creating a team in a hierarchy traditionally requires 3 calls:

1. **Check:** Is the parent valid and not too deep?

2. **Write 1:** Insert the team record.

3. **Write 2:** Insert the self-reference into the Closure Table.



At high concurrency, these 3 calls represent a significant latency tax and a window for race conditions.



### Optimization: PostgreSQL CTE with `INSERT`

**Pattern:** We moved the logic into a single raw SQL query using `WITH ... INSERT`.

*   **Atomic Validation:** The `INSERT ... SELECT` pattern only executes if the `WHERE` clause (which checks parent existence and depth) returns a row.

*   **Multi-Table chaining:** The `RETURNING` clause of the first insert feeds directly into the second insert (the Closure Table).

*   **Result:** 3 round-trips collapsed into **1 atomic call**.

*   **Deferred Diagnostics:** If the call returns "0 rows affected," the application then runs standard DSL queries to explain *why* (e.g., "Parent not found") to maintain developer experience without sacrificing production speed.



**Win:** Minimal latency for the "Happy Path" while maintaining strict data integrity.
