# Low-Level Design (LLD): Universal Cascading Cleanup

## 1. Introduction
This document details the low-level implementation of the Universal Cascading Cleanup matrix, ensuring all entity deletions (Projects, Teams, Tasks, Members) are processed asynchronously in high-throughput chunks.

## 2. Event Routing (WorkspaceConsumer)

The `WorkspaceConsumer` acts as the central router for the `workspace-activity` topic.

1.  **Domain Events (Triggers):**
    *   `ProjectDeleted` -> Emits `ProjectPurgeRequested`.
    *   `ProjectMembersRemoved` -> Emits `MemberCleanupRequested`.
    *   `TeamDeleted` -> Emits `SubTeamsPurgeRequested` & `TeamTasksUnassignRequested`.
    *   `TaskDeleted` -> Emits `SubTasksPurgeRequested`.
2.  **Internal Events (Workers):**
    *   These events are picked up in subsequent Kafka batches and routed to specific methods in `TaskEventHandler` and `TeamEventHandler` to perform the actual chunky queries.

## 3. The "Chunky Delete" SQL Patterns

### 3.1. Sub-Task Purge (Materialized Path)
Uses the `path` captured before root task deletion.
```sql
DELETE FROM project_tasks 
WHERE id IN (
    SELECT id FROM project_tasks 
    WHERE fk_project_id = ?::uuid AND path LIKE ? 
    LIMIT ?
)
```

### 3.2. Sub-Team Purge
Uses the list of descendant IDs captured via the closure table before root team deletion.
```sql
WITH target_teams AS (
    SELECT id FROM project_teams 
    WHERE fk_project_id = ?::uuid AND id = ANY(?) 
    LIMIT ?
),
deleted_members AS ( DELETE FROM project_team_members WHERE fk_team_id IN (SELECT id FROM target_teams) ),
deleted_closure AS ( DELETE FROM project_team_closure WHERE fk_team_id IN (SELECT id FROM target_teams) OR fk_child_id IN (SELECT id FROM target_teams) )
DELETE FROM project_teams WHERE id IN (SELECT id FROM target_teams)
```

### 3.3. Member Unassign / Team Unassign
Unassigns tasks in chunks without locking the whole table.
```sql
UPDATE project_tasks 
SET fk_assigned_team_member = NULL, updated_at = NOW(), version = version + 1
WHERE id IN (
    SELECT id FROM project_tasks 
    WHERE fk_project_id = ?::uuid AND fk_assigned_team_member = ANY(?)
    LIMIT ?
)
```

## 4. Self-Re-emission Loop
Every Chunky handler follows this loop:
1. Execute chunky SQL query (Limit = X).
2. If `rowsAffected > 0` (or `== X`), assume more work exists.
3. `kafkaTemplate.send(TOPIC, projectId, sameEvent)`.
4. Acknowledge offset. 
This prevents Head-of-Line blocking and naturally drains massive datasets.
