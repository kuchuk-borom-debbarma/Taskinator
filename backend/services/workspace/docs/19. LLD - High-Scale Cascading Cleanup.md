# Low-Level Design (LLD): Universal Cascading Cleanup (Distributed)

## 1. Introduction
This LLD details the decentralized implementation of the Universal Cascading Cleanup matrix. It utilizes Kafka's ability to broadcast events to multiple consumer groups, allowing different domains to process the same trigger independently.

## 2. Distributed Routing

All events are produced to the `workspace-activity` topic, keyed by `projectId`.

### 2.1. Project Consumer (`groupId: project-service-group`)
- **Triggers:** `ProjectDeleted`, `ProjectMembersRemoved`.
- **Actions:** Purges core project metadata and emits orchestration events (`ProjectTeamsPurgeRequested`, `ProjectTasksPurgeRequested`) to trigger other domains.

### 2.2. Team Consumer (`groupId: team-service-group`)
- **Triggers:** `TeamDeleted`, `ProjectTeamsPurgeRequested`, `MemberTeamCleanupRequested`.
- **Actions:** Performs chunky deletions of team hierarchies and memberships.

### 2.3. Task Consumer (`groupId: task-service-group`)
- **Triggers:** `TaskDeleted`, `ProjectTasksPurgeRequested`, `TeamTasksUnassignRequested`, `MemberTaskCleanupRequested`.
- **Actions:** Performs heavy chunky deletions of task sub-trees and handles task unassignments.

## 3. The "Chunky" Worker Loop

Each consumer implements idempotent worker methods following this pattern:
1.  Receive event (e.g., `PurgeTasks`).
2.  Execute `DELETE ... LIMIT 5000`.
3.  If `rowsDeleted == 5000`: More work exists. Re-produce the *same* event back to Kafka.
4.  If `rowsDeleted < 5000`: Domain is clean.
5.  `ack.acknowledge()`

## 4. Why this is superior to a Single Orchestrator
- **Zero Cross-Talk:** If the Task database is under heavy load, the Team cleanup can still finish instantly.
- **Granular Retries:** If a `TeamTasksUnassign` fails, Kafka retries only that event within the `TaskConsumer` group. The `TeamConsumer` group is unaffected.
