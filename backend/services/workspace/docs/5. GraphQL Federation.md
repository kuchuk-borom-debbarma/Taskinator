# GraphQL Federation (The "Stitched" Graph)

In our architecture, no single service knows everything. Instead, we use **Apollo Federation** to combine multiple services into one single API.

## 1. The Big Picture
*   **Identity Service (Bun/Hono):** Owns the `User` type (usernames, passwords, emails).
*   **Workspace Service (Spring):** Owns `Projects` and `Teams`.
*   **The Gateway:** The single entry point for the frontend. It routes requests to the right service.

## 2. Key Concepts

### Entity (`@key`)
Any object that can be "joined" across services must have a `@key`.
*   Example: In Workspace, we say `Project @key(fields: "id")`. This means if a "Task Service" has a Project ID, it can ask us for the Project's name.

### Extension (`extend type`)
This is how we "plug into" other services.
*   We don't own the `User`, but we want users to have a `projects` field.
*   We `extend type User` and add the field. The Gateway handles the "stitching".

### Representations (The "Handshake")
When we return a user (like a Project Owner), we don't return their name. We return a **Representation**:
```json
{ "__typename": "User", "id": "user-123" }
```
The Gateway sees this and says: *"Aha! I need to ask the Identity Service for the username of user-123."*

## 3. Service Independence (Where to define what?)

A core rule of Federation is **Separation of Concerns**. We avoid "circular dependencies" by following these rules:

### Rule 1: The Source of Truth stays CLEAN
The **Identity Service** should not know that Projects exist. Its schema only defines the User profile. This allows you to add or remove new services (like "Billing" or "Tasks") without ever touching the Identity code.

### Rule 2: The Extension owns the LINK
Since the **Workspace Service** is the one providing the `projects`, it is responsible for "hooking" into the User. It defines the "User Skeleton" and adds the `projects` field to it.

| Feature | Defined In | Known By Identity? |
| :--- | :--- | :--- |
| `User.username` | Identity Service | Yes |
| `User.projects` | Workspace Service | **No** |
| `Project.name` | Workspace Service | No |

## 4. Request Flow
1.  **Frontend** asks for `user { username projects { name } }`.
2.  **Gateway** asks **Identity** for the `username`.
3.  **Gateway** sees that `projects` lives in **Workspace**, so it asks us: *"Here is User ID '123', give me their projects."*
4.  **Gateway** merges both answers and sends one JSON to the user.
