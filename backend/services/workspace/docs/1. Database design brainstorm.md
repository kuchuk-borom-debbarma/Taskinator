# Database Design Brainstorm & Architecture

## Context
- **Target Scale:** 10,000 requests per second (RPS).
- **Environment:** Read-heavy workload with specific write-heavy hotspots (Tasks).
- **Core Technology:** PostgreSQL (Exposed ORM in Kotlin).

## Domain Analysis & Observations

### 1. Projects
- **Characteristics:** Extremely Read-Heavy. Created rarely, queried constantly.
- **Key Queries:** "Get Project by ID", "List my projects", "Get Dashboard Stats".
- **Scaling Strategy:**
    - **Caching:** Aggressive caching is possible due to low volatility.
    - **Denormalization:** Storing "Active Task Count" and "Member Count" directly on the `Project` table avoids expensive `COUNT(*)` queries on the dashboard.

### 2. Teams
- **Characteristics:** Read-Heavy, Hierarchical, Security Critical.
- **Hierarchy:** Teams have a graph structure (Company -> Engineering -> Backend).
- **Security:** "Permission Bubbling" is critical (e.g., A manager of a parent team implicitly has access to child team resources).
- **Write Patterns:** Teams are moved or re-structured very infrequently (e.g., once a month).

### 3. Tasks
- **Characteristics:** High Volume (Millions/Billions of rows), Mixed Read/Write.
- **Volatility:**
    - **Status Changes:** Frequent (Kanban moves).
    - **Hierarchy Changes:** Rare (Re-parenting a sub-task).
- **Hierarchy:** Deep nesting (Epic -> Story -> Task -> Subtask).
- **Sorting:** Drag-and-drop ordering (Lexorank/Double) is essential to avoid "Write Storms" where moving one task updates 500 others.

---

## Architectural Decisions

### 1. Database Sharding Strategy
**Sharding Key:** `project_id`
- **Rationale:** 99% of data access is scoped to a single project.
- **Benefit:** Allows horizontal scaling. Project A can live on Node 1, Project B on Node 2. No cross-shard joins are required for standard board operations.

### 2. Handling Hierarchy (The Hybrid Approach)

We observed that "One size fits all" fails for hierarchy at scale. We chose a hybrid approach:

#### **A. Teams: Closure Table**
- **Implementation:** A separate table `team_hierarchy` storing every ancestor-descendant pair.
- **Why Chosen:**
    - **Permission Speed:** Checking "Does User U have access to Team X?" becomes a single, instant SQL `JOIN`.
    - **Volume:** Team counts are low (hundreds), so the Closure Table size is negligible.
- **Trade-off:** "Moving" a team is complex (many rows to update), but since team moves are rare, this is acceptable.

#### **B. Tasks: Root-ID + Materialized Path**
- **Implementation:** Columns on the `Tasks` table:
    - `parent_id` (Direct parent for UI).
    - `root_id` (Top-level Epic/Goal ID).
    - `path` (String: `root_id/parent_id/task_id`).
- **Why Chosen:**
    - **Volume:** With millions of tasks, a Closure Table would be billions of rows (too big).
    - **Read Speed:** "Get entire sub-tree" is a fast prefix index scan (`WHERE path LIKE 'abc/%'`).
    - **Sharding:** All hierarchy data lives in the same row, on the same shard.
- **Trade-off:** Updating a path requires a string replacement, but since re-parenting is rare, it's efficient.

### 3. Task Filtering & Search
- **Problem:** Complex filters (e.g., "Tasks in 'In Progress' status, assigned to Team A, excluding Tag B") are slow in standard SQL at 10k RPS.
- **Solution (Read-Model Pattern):**
    - **Postgres:** Source of Truth for writes and transactional integrity.
    - **ElasticSearch/OpenSearch:** (Future) Tasks are projected here for complex filtering.

## Schema Overview

### Projects Table (Read Optimized)
- `id` (UUID, PK)
- `active_task_count` (Integer, Denormalized)
- `member_count` (Integer, Denormalized)
- *Optimization:* Index on `owner_id`.

### Project Members Table (Identity Denormalization)
- `project_id` (UUID, Part of Composite PK) - Shard Key.
- `user_id` (UUID, Part of Composite PK).
- `display_name` (String) - **Denormalized** for 10k RPS. Allows fetching Task + User info in one query without joins/API calls.
- `avatar_url` (String, Nullable) - **Denormalized** to speed up Kanban board rendering.
- `role` (String).
- *Optimization:* **Composite Primary Key** `(project_id, user_id)` for index-only scans and clustered data access.

### Teams Table (Security Optimized)
- `id` (UUID, PK)
- `project_id` (FK, Shard Key).
- *Optimization:* **Closure Table** (`ancestor_id`, `descendant_id`, `depth`) for hierarchy.

### Team Members Table (Sharding Safety)
- `team_id` (UUID, Part of Composite PK).
- `user_id` (UUID, Part of Composite PK).
- `project_id` (UUID) - **Redundant Shard Key**. Ensures all team membership data lives on the same physical shard as the project.
- *Optimization:* **Composite Primary Key** `(team_id, user_id)`.

### Tasks Table (Write Optimized)
- `id` (UUID, PK)
- `project_id` (FK, Shard Key)
- `status` (String/Enum)
- `lexo_rank` (String) - For O(1) drag-and-drop reordering.
- `version` (Long) - For Optimistic Locking.
- **Hierarchy Columns:**
    - `root_id` (UUID) - Instant access to Epics.
    - `path` (Text) - Instant access to sub-trees.
- *Optimization:* Composite Index on `(project_id, status, lexo_rank)` for instant Kanban board loading.

## Why this Architecture handles 10k RPS



1.  **Zero "Scan" Queries:** Every critical read (Load Board, Check Permission) uses a precise Index or PK lookup.

2.  **No "Count" Queries:** Dashboard stats are pre-calculated (Denormalized).

3.  **Writes are Isolated:** Sharding by `project_id` ensures that high load on one project doesn't degrade the performance of others.

4.  **Optimistic Locking:** Prevents database-level row locks during concurrent edits, keeping throughput high.

5.  **Efficient Hierarchy:** We avoid recursive CTEs (slow) and massive join tables for tasks (bloated), utilizing the best tool for each specific domain size.

## Design Rules & Core Lessons



1.  **Strategic Denormalization:** Denormalize data that is read-heavy but does not require real-time transactional consistency. 

    *   *Example:* Store user `display_name` and `avatar_url` in the `ProjectMembers` table. This eliminates massive JOINs or cross-service API calls when loading high-traffic pages like a Kanban board.

2.  **Hierarchy vs. Volume Rule:** Choose hierarchy strategies based on row volume, not just structure.

    *   **Low Volume (Teams):** Use a **Closure Table**. It is the gold standard for performance and security but has high index maintenance.

    *   **High Volume (Tasks):** Use a **Materialized Path + RootID**. It saves massive index costs and storage bloat while keeping "fetch tree" operations fast and sharding-friendly.

3.  **Sharding Safety First:** Always include the Sharding Key (`project_id`) on every child table (Teams, Tasks, Members), even if it feels redundant. This ensures all related data is physically co-located on the same shard, preventing expensive cross-node traffic.

4.  **O(1) Drag-and-Drop:** Never use integers for UI sequencing. Use **Lexorank (Strings)** or **Doubles**. This ensures that moving a task is always a single-row update, preventing "Write Storms" that occur when shifting entire lists.

5.  **Performance > Normalization:** At 10,000 RPS, a slightly larger row size is a cheap price to pay to avoid the computational overhead of complex relational joins or the latency of network calls.
