# Kafka & Event-Driven Architecture (EDA)

This document outlines the strategy for scaling Taskinator beyond synchronous API calls using Kafka. It ensures high availability, flat latency, and eventually consistent background processing.

## 1. Core Philosophy: "Lean Write, Heavy Background"

To maintain 10k RPS, the Workspace Service follows a strict "Lean Write" policy. The API performs the minimum work required to maintain primary data integrity and then emits an event for everything else.

*   **Synchronous (API):** Primary record insertion, security validation, and initial parent-link.
*   **Asynchronous (Kafka):** Hierarchy expansion (Closure Table/Path), recursive deletions, stats updates, and search indexing.

---

## 2. Kafka Structural Design

### Topics & Partitioning
*   **Topic Naming:** `<domain>.<entity>.<action>` (e.g., `workspace.tasks.created`, `workspace.teams.deleted`).
*   **The Shard Key (Partitioning):** All events MUST use the `projectId` as the **Kafka Partition Key**.
    *   **Guarantee:** This ensures that all events for a specific project are processed in strict chronological order by the same consumer instance.
    *   **Scaling:** We can increase the number of partitions to scale horizontally as the number of projects grows.

### Offsets & Reliability
*   **The "Bookmark" Strategy:** Consumers track their progress via **Offsets**. 
*   **Fault Tolerance:** If a background worker (e.g., the Task Deletion worker) crashes, it will resume from its last committed offset upon restart, ensuring no tasks are left in a "zombie" state.

---

## 3. Critical Patterns

### The Transactional Outbox
To ensure the Database and Kafka are always in sync, we do not send to Kafka directly from the Service layer.
1.  **Atomic Write:** The raw SQL CTE that modifies a Team/Task also inserts a record into an `outbox_events` table within the same transaction.
2.  **The Relay:** A background process polls the `outbox_events` table and publishes messages to Kafka.
3.  **Result:** No "Ghost Events" (where DB fails but Kafka sends) and no "Lost Events" (where DB succeeds but Kafka fails).

### Background Workers (The "Consumers")
*   **Hierarchy Worker:** Listens for `TEAM_CREATED`. It expands the Closure Table paths while the user is already interacting with the new team.
*   **Cleanup Worker:** Listens for `TASK_DELETED` or `TEAM_DELETED`. It performs recursive batch deletions of sub-entities to prevent API timeouts.
*   **Stats Worker:** Listens for membership changes and increments/decrements `members_count` in the `Projects` table.

---

## 4. Spring Implementation & Scaling

### Integrated Workers
The background listeners are implemented in the same Spring Boot project using `@KafkaListener`. This allows the workers to reuse the **Exposed Repository** logic and domain models without code duplication.

### Deployment Scaling (Profiles)
While the code is shared, we can scale the API and Workers independently using Spring Profiles:
*   **API Mode (`-Dspring.profiles.active=api`):** Disables Kafka listeners and optimizes for high-throughput HTTP traffic.
*   **Worker Mode (`-Dspring.profiles.active=worker`):** Disables the Web server (Tomcat/Netty) and only runs the Kafka consumer threads.
*   **Why?** At 10k RPS, we don't want a heavy recursive delete operation to steal CPU cycles from the API's response time.

## 5. Event Schema (Example: Task Created)

Events are serialized as JSON or Avro to ensure compatibility across different services.

```json
{
  "eventId": "uuid-v7",
  "type": "TASK_CREATED",
  "timestamp": "2026-02-19T14:00:00Z",
  "payload": {
    "taskId": "...",
    "projectId": "...", // The Partition Key
    "parentTaskId": "...",
    "title": "Build Kafka Docs",
    "createdBy": "..."
  }
}
```

## 6. Scaling 10k RPS with Kafka
*   **Consumer Groups:** Multiple instances of the Workspace Service can join the same consumer group. Kafka will balance the partitions across them.
*   **Backpressure:** If the database is under heavy load, consumers can slow down their reading speed without affecting the main API's ability to accept new requests.
