# Workspace Event-Driven Architecture

This document describes the high-performance, event-driven orchestration used in the Workspace service to handle complex cascading operations and ensure 10k+ RPS scalability.

## 1. The Architectural Pattern: Ingest-Buffer-Drain

Taskinator uses a decoupled write path to separate user-facing latency from heavy background computations.

1.  **Ingest (Producers):** GraphQL Mutation Fetchers perform the primary, atomic database write and immediately fire an "Activity Event" to Kafka.
2.  **Buffer (Kafka):** The `workspace-activity` topic acts as a durable, ordered buffer. All events for a single `projectId` are sent to the same Kafka partition to ensure strict causal ordering.
3.  **Drain (Consumers):** Domain-specific consumers (Project, Team, Task) listen to the stream and perform secondary operations like cascading deletes, hierarchy re-computations, and cross-domain cleanups.

---

## 2. Event Producers (Mutation Fetchers)

Events are fired **exclusively** from the Controller layer (`controllers/*.MutationFetcher.kt`). This ensures that an event is produced exactly once per external request.

| Domain | Producer | Primary Sync Action | Event Produced |
| :--- | :--- | :--- | :--- |
| **Project** | `ProjectMutationFetcher` | Create/Rename/Delete Project | `ProjectCreated`, `ProjectRenamed`, `ProjectDeleted`, `ProjectMembersAdded`, `ProjectMembersRemoved` |
| **Team** | `TeamMutationFetcher` | Create/Update/Delete Team | `TeamCreated`, `TeamRenamed`, `TeamDeleted`, `TeamMembersAdded`, `TeamMembersRemoved` |
| **Task** | `TaskMutationFetcher` | Create/Assign/Update Task | `TaskCreated`, `TaskAssigned`, `TaskStatusUpdated`, `TaskDeleted` |

## 3. Domain Consumers & Orchestration

The system uses three specialized consumers, each belonging to its own Consumer Group to allow independent scaling.

### A. Project Consumer (`project-service-group`)
Responsible for fanning out high-level project changes to other domains.
*   **On `ProjectDeleted`:** 
    1.  Deletes project members synchronously.
    2.  Produces `ProjectTeamsPurgeRequested` (for Teams).
    3.  Produces `ProjectTasksPurgeRequested` (for Tasks).
*   **On `ProjectMembersRemoved`:** 
    1.  Produces `MemberTeamCleanupRequested` and `MemberTaskCleanupRequested`.

### B. Team Consumer (`team-service-group`)
Handles hierarchy-related side effects and team cleanup.
*   **On `TeamDeleted`:** 
    1.  Fires `SubTeamsPurgeRequested` for all descendants.
    2.  Fires `TeamTasksUnassignRequested` to the Task domain.
*   **Recursive Batching:** Handles `ProjectTeamsPurgeRequested` and `SubTeamsPurgeRequested` in chunks (e.g., 1000 records). If more records remain, it re-emits the event to itself to continue in the next cycle.

### C. Task Consumer (`task-service-group`)
The "Heavy Lifter" for task-related cascading operations.
*   **On `TaskDeleted`:** Uses the captured `path` to fire a `SubTasksPurgeRequested`.
*   **Cascading Purge:** Efficiently handles `ProjectTasksPurgeRequested` and `SubTasksPurgeRequested` using `Materialized Path` indexed scans.
*   **Unassignment:** Processes `TeamTasksUnassignRequested` and `MemberTaskCleanupRequested` to ensure no tasks point to non-existent teams/members.

## 4. The Multi-Consumer Group Advantage

All three domain-specific consumers listen to the **same** `workspace-activity` topic but operate within their own unique **Consumer Group IDs**. This "Fan-out" pattern provides several critical high-scale advantages:

1.  **Independent Scaling:** Since each domain has its own group ID (`project-service-group`, `team-service-group`, `task-service-group`), you can scale them independently. If the Task domain is under extreme load from millions of sub-task deletions, you can spin up more Task Consumer instances without affecting the Project or Team consumers.
2.  **Parallel Execution:** When a high-level event like `ProjectDeleted` is fired, all three consumers receive it simultaneously. The Project consumer cleans up metadata, the Team consumer starts purging teams, and the Task consumer starts purging tasks in parallel. This drastically reduces the total "Wall Clock Time" for large cascading cleanups.
3.  **Fault Isolation:** If the `TaskConsumer` crashes while processing a particularly heavy batch, Kafka only re-delivers that batch to the `task-service-group`. The Project and Team consumers, which may have already succeeded, are not forced to re-process the same work.
4.  **Domain Autonomy:** Each consumer only processes events relevant to its domain (e.g., `if (event is TeamEvent)`). This allows a single "Unified Stream" to orchestrate the entire system while keeping the business logic for each domain isolated and clean.

## 5. The "Filter" Check & Causal Ordering

A common question is whether delivering every event to every consumer creates a performance bottleneck (e.g., the Task Consumer receiving `ProjectCreated` events). 

### The "Skip" Efficiency
Each consumer uses a simple in-memory type check (e.g., `if (event is TeamEvent)`). This check takes **nanoseconds** to execute. Compared to the latency of a database write or a network call, the overhead of skipping irrelevant messages is negligible.

### The Causal Ordering Benefit (The "Why")
The primary reason for using a **Unified Topic** for all domain events is to guarantee **Causal Ordering**. 

By keying all events by `projectId`, we ensure they land in the same Kafka partition and are processed in the exact order they were produced:
1.  **Guaranteed Sequence:** A `TeamCreated` event will **always** be delivered to the Team Consumer *after* the `ProjectCreated` event has been delivered to the Project Consumer. 
2.  **No Race Conditions:** If we used separate topics for each domain, a "Team Created" event might arrive at its consumer *before* the Project exists in the system due to network jitter or partition lag.
3.  **Unified State:** The Unified Stream ensures that the entire system moves through its lifecycle in a logical, ordered sequence, preventing "Orphaned" data (e.g., a Team without a Project).

## 6. Reliability & High-Scale Design

### Partitioning Strategy
All events are keyed by `projectId`.
*   **Benefit:** Ensures that for any given project, a `TeamDeleted` event is always processed *before* a `TeamTasksUnassignRequested` event if they were fired in that order.

### Zero-OOM Batching
Consumers never load entire datasets into memory. They use **Atomic Batch SQL** (e.g., `DELETE ... WHERE id IN (SELECT id ... LIMIT 5000)`). If the `rowsAffected` equals the batch size, the consumer knows there is more work and re-sends the event to Kafka.

### Idempotency
All creation events (Project/Team/Task) include an `idempotencyKey`. The database enforces a `UNIQUE` constraint on this key, ensuring that even if Kafka re-delivers an event (at-least-once delivery), the system remains consistent.

### Captured Scope
In delete events, we capture the "Scope" (like the `path` of a task or `descendantIds` of a team) **before** the record is gone. This allows background workers to clean up related data without needing to perform expensive lookups on already-deleted parents.
