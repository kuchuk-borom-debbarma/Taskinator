# 10. Read Path Optimization (GraphQL DataLoaders & Lazy Caching)

To support the high-scale writes designed in the previous documents, the **Read Path** must be equally efficient. This document outlines the strategy for solving the N+1 problem and ensuring low-latency reads using GraphQL DataLoaders and a Lazy Database-First caching model.

## 1. The N+1 Problem in Taskinator
With recursive tasks and complex relationships (Owner, Project, Team), a single GraphQL query could trigger hundreds of database round-trips.
*   **With DataLoaders:** Fetching 100 tasks with their owners = 1 query for tasks + 1 batch query for owners = **2 total queries**.

---

## 2. Low-Level Implementation: MappedBatchLoader
We use `MappedBatchLoader` to ensure type safety and handle cases where the database might return results in a different order than requested.

### The Lazy Database-First Logic
When a DataLoader is invoked to fetch a batch of IDs (e.g., `ownerIds` or `parentTaskIds`):

1.  **Phase 1: Database-as-Truth (L2 Storage)**
    Execute a single `SELECT ... WHERE id IN (...)` for the requested IDs.
    *   *Rationale:* We do not attempt to read "In-Flight" data from Redis to avoid complex consistency bugs. Data is only visible once it is successfully committed to PostgreSQL.
2.  **Phase 2: Consolidation**
    Convert the Database results into a `Map<ID, Entity>`.
3.  **Phase 3: Post-Fetch Caching (L1 Cache)**
    Once data is successfully read from the DB, the result is asynchronously pushed to **Redis** with a short TTL. This speeds up subsequent identical requests without compromising the "Database-as-Truth" principle.

---

## 3. Recursive Task Resolution
Taskinator allows tasks to be nested up to 50 levels deep. DataLoaders optimize this "Tree Walk":

*   **Breadth-First Batching:** The DataLoader engine waits for all fields at a specific depth of the tree to be requested before executing the batch.
*   **Complexity Limit:** A query fetching 5 levels of tasks will execute exactly **5 batch queries**, regardless of the total number of tasks in the tree.

```kotlin
@DgsDataLoader(name = "subtasks")
class SubtaskDataLoader(val taskService: TaskService) : MappedBatchLoader<UUID, List<Task>> {
    override fun load(keys: Set<UUID>): CompletionStage<Map<UUID, List<Task>>> {
        return CompletableFuture.supplyAsync {
            // Fetch all children for all parent IDs in one query
            taskService.findChildrenByParentIds(keys)
        }
    }
}
```

---

## 4. Federated DataLoaders (Cross-Service)
Since Taskinator uses **Apollo Federation**, some data (like `User` profiles) lives in the **Identity Service**, while `Tasks` live in the **Workspace Service**.

*   **The Solution:** The DataLoaders load function calls the Identity Service via a high-performance batch endpoint.
    *   *Batch Request:* `POST /internal/users/batch-find { ids: [...] }`

---

## 5. Caching Strategy & Scope
*   **Request-Scoped Cache:** DataLoaders maintain an internal cache **only for the duration of a single GraphQL request**. This ensures that if the same User is requested 10 times in one query, the DB is hit only once.
*   **Zero Stale Data:** By scoping the internal cache to the request, we avoid the complexity of cache invalidation that plagues global caches.

---

## 6. Performance Tuning
*   **Max Batch Size:** Set to 1,000 to avoid hitting PostgreSQLs limit on `IN` clause parameters.
*   **Dispatcher Threads:** Use a dedicated `virtual-thread-per-task` (Java 21) or a custom ThreadPool for DataLoaders.

## 7. Summary of Read Path Flow
1.  **GraphQL Engine** parses query.
2.  **DataFetchers** return `CompletableFuture`.
3.  **DataLoader Dispatcher** collects all IDs at the current tree level.
4.  **BatchLoader** performs Database Read (Source of Truth).
5.  **Entities** are returned to user and lazily cached in Redis for future reads.
