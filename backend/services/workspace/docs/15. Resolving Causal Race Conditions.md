# 15. Resolving Causal Race Conditions (The Unified Entity Stream)

This document outlines the implementation strategy for eliminating race conditions between Project creation and Task creation by unifying all Workspace mutations into a single Kafka stream.

## 1. The Problem: "Wait-and-See" is a Patch, Not a Solution
Currently, Projects are written **synchronously** to the DB, while Tasks are sent **asynchronously** to Kafka. This results in two separate paths to the database:

1.  **Path A (Sync)**: Project Insert → DB Flush → DB Commit.
2.  **Path B (Async)**: Task Event → Kafka → Worker → Project Check → Task Insert.

If Path B is faster than Path A (due to DB latency or network jitter), the Task Worker will fail because the Project doesn't exist yet. Our current **100ms retry** is a temporary "patch" that adds latency and instability.

---

## 2. The Solution: Unified Entity Stream
We will move **Projects and Teams** to the same asynchronous path as Tasks. By doing this, we leverage Kafka's **Partition Ordering Guarantee**.

### How it works:
1.  **API Ingest**: All Workspace mutations (Create Project, Create Team, Create Task) are pushed to the **same Kafka topic** (`workspace-activity`).
2.  **Partition Key**: Every event uses the `projectId` as the partition key.
3.  **Sequential Processing**: Kafka guarantees that events in a single partition are delivered to the worker in the exact order they were produced.

**The Sequential Chain:**
`[Offset 1]: ProjectCreated` → `[Offset 2]: TeamCreated` → `[Offset 3]: TaskCreated`

The worker will **physically never see** the Task before it has finished committing the Project to the database.

---

## 3. Implementation Steps

### Step 1: Update the Event Schema (`Events.kt`)
Add new event types for Projects and Teams to the `TaskEvent` sealed class (or rename it to `WorkspaceEvent`).
- `ProjectCreated(id, name, owner, ...)`
- `TeamCreated(projectId, teamId, name, ...)`

### Step 2: Convert API Fetchers
Modify `ProjectMutationFetcher` and `TeamMutationFetcher` to:
1.  **Generate UUIDs** immediately (ID-First).
2.  **Produce events** to Kafka instead of calling the service directly.
3.  **Return 202 Accepted** to the client.

### Step 3: Update the Worker (`TaskConsumer.kt`)
Expand the consumer to handle the new event types:
1.  **If ProjectCreated**: Call `projectService.createProject()`.
2.  **If TeamCreated**: Call `teamService.createTeam()`.
3.  **If TaskCreated**: Call `taskService.createTask()`.

### Step 4: Remove the "Wait-and-See" logic
Once all events flow through Kafka, the `executeWithRetry` loop in the consumer becomes redundant and can be removed, as order is now guaranteed by the infrastructure.

---

## 4. Performance & Consistency Benefits
*   **Zero Race Conditions**: Natural causal ordering via Kafka partitions.
*   **Reduced Latency**: All Workspace mutations now return in <10ms.
*   **Infinite Scalability**: Adding more partitions allows the system to scale to millions of workspace operations per second without DB contention.
