# Technical Scaling: Architecture for 10k RPS

This document details the high-performance patterns implemented to ensure the Workspace service remains stable and responsive under extreme loads.

## 1. Database Write Optimizations

### One-Statement Operations
*   **INSERT ... RETURNING:** Utilized `insert { ... }.resultedValues` to perform a write and fetch the full record (including DB defaults) in a **single database round-trip**.
*   **Atomic 1-Call Multi-Table Chaining:** Used PostgreSQL CTEs (`WITH ... INSERT`) to combine **validation** (depth/parent check), **team insertion**, and **closure table self-reference** into a single atomic statement. This collapses what is normally 3 round-trips into 1.
*   **Atomic Deletion:** Implemented a "Verify-then-Cleanup" sequence. The primary record is deleted first with a version check; only upon success is the secondary hierarchy data (Closure Table) purged.

### Bulk Operations
*   **JDBC Batch Rewriting:** Configured `reWriteBatchedInserts=true`. This reduces network overhead by collapsing multiple inserts into a single command.
*   **Validated Batching:** Member additions use a **2-call sweep**:
    1.  **Filter:** The DB validates which IDs belong to the project.
    2.  **Batch Write:** Only valid IDs are written in a high-throughput batch.

### Sharding Compatibility
*   **Explicit Shard Keys:** Every table stores the `projectId` or `ownerId`. Related data is co-located on the same shard to avoid cross-node traffic.

## 2. Read Optimization Strategy

### Zero-JOIN Denormalization
*   Storing `username` and `avatarUrl` directly in the Membership tables. This allows the UI to render board participants instantly with a single primary-key lookup, avoiding slow JOINs with a global `Users` table.

### Hierarchy (The Closure Table)
*   **O(1) Traversal:** Replaced slow Recursive CTEs with a pre-computed **Closure Table**. Finding all sub-teams is a simple indexed scan.

---

## 3. Latency & Concurrency

### Optimistic Locking
*   **Lock-Free Scaling:** Uses a `version` column for all updates/deletes. Thousands of users can read concurrently without blocking each other.

### Event-Driven Hierarchy
*   **Sync/Async Split:**
    *   **Synchronous:** Lean write of Team record + Depth 0 visibility (< 50ms).
    *   **Asynchronous:** A background listener copies the 50+ ancestral paths.
    *   Ensures the API stays responsive during complex tree modifications.

---

## 4. Stability & Security Guards

### DoS & OOM Protection
*   **Coerced Pagination:** Enforced a `MAX_LIMIT = 100` at the service layer.
*   **Deterministic Sort:** Every paginated query uses the record `id` as a tie-breaker to prevent "item jumping" across pages.

### Boundary Protection
*   **Depth Guard:** An O(log N) check prevents hierarchies from exceeding 50 levels.
*   **UTC Standardization:** Standardized on `ZoneOffset.UTC` for all timestamps to prevent drift in distributed environments.
