# Technical Scaling: Architecture for 10k RPS

This document details the high-performance patterns implemented to ensure the Workspace service remains stable and responsive under extreme loads (target: 10,000 requests per second).

## 1. Database Write Optimizations

### Bulk Operations
*   **JDBC Batch Rewriting:** Configured `reWriteBatchedInserts=true` in the datasource. This converts hundreds of individual `INSERT` statements into a single multi-value SQL command, reducing network round-trips by 99%.
*   **Streaming Inserts:** Used `shouldReturnGeneratedValues = false` during batch inserts. This prevents the application from waiting for the database to return every generated ID, allowing for maximum write throughput.
*   **Idempotency:** Utilized `ignore = true` (INSERT IGNORE) for member additions. This handles network retries gracefully at high scale without generating error logs.

### Sharding Compatibility
*   **Explicit Shard Keys:** Every table (Teams, Members, Tasks) explicitly stores the `projectId` or `ownerId`. This ensures that all data related to a project is physically co-located on the same shard, preventing expensive cross-node network traffic.

---

## 2. Read Optimization Strategy

### Denormalization
*   **Zero-JOIN Memberships:** Storing `username`, `displayName`, and `avatarUrl` directly in the `ProjectMembers` and `ProjectTeamMembers` tables. This allows the UI to render board participants instantly with a single primary-key lookup, avoiding slow JOINs with a massive global `Users` table.

### Hierarchy (The Closure Table)
*   **O(1) Traversal:** Instead of using slow Recursive CTEs (Common Table Expressions) to find team sub-structures, we use a **Closure Table**. Every possible path from parent to descendant is pre-computed.
*   **Fast Descendant Search:** Finding all members of a department and its 50 sub-teams is reduced to a single indexed `SELECT` query on the closure table.

---

## 3. Concurrency & Integrity

### Optimistic Locking
*   **Lock-Free Updates:** We use a `version` column for all updates. This allows thousands of users to read the same project concurrently without ever blocking each other at the database row level. Conflicts are handled at the application layer by throwing `ConcurrencyException`.

### Event-Driven Hierarchy
*   **Latency Decoupling:** The "heavy" computation of hierarchy paths is moved to an **Async Event**. 
    *   **Synchronous Path:** Inserts the team and a 'depth 0' entry (< 50ms).
    *   **Asynchronous Path:** An event listener copies the ancestor paths in the background.
    *   This ensures the API remains responsive even if the hierarchy is deep.

---

## 4. Stability & Security Guards

### DoS Protection
*   **Pagination Limits:** Every query that supports `limit` is governed by a `MAX_LIMIT = 100` constant in the service layer. This prevents Out-Of-Memory (OOM) crashes if a malicious user requests millions of rows.
*   **Deterministic Sort:** Every paginated query uses the record `id` as a final tie-breaker in `orderBy`. This prevents "item jumping" across pages during high-frequency writes.

### Boundary Protection
*   **Depth Guard:** An O(log N) check ensures hierarchies never exceed 50 levels, protecting the database from resource-exhaustion attacks via infinite trees.
*   **UTC Standardization:** Every timestamp is forced to `ZoneOffset.UTC` at the application level to prevent time-drift issues in distributed environments.
