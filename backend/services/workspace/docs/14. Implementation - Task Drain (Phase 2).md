# 14. Implementation - Task Drain (Phase 2)

This document details the implementation of the "Drain" phase, where buffered Kafka events are persisted to the PostgreSQL database in high-efficiency batches.

## 1. The "Drain" Lifecycle
The `TaskConsumer` acts as the "Sponge" that absorbs the high-frequency event stream and squeezes it into the relational database.

1.  **Batch Polling**: The consumer pulls up to 500 events from Kafka in a single poll.
2.  **Transaction Boundary**: A single database transaction is opened for the entire batch.
3.  **Entity Mapping**: Events are grouped by type (Created, Updated, Deleted).
4.  **Database Persistence**: The consumer executes optimized SQL via `TaskQueries`.
5.  **Manual Acknowledgment (ACK)**: The Kafka offset is moved forward **only** if the database transaction commits successfully.

---

## 2. Low-Level Mechanics

### A. Batch Listener Configuration (`KafkaConfiguration.kt`)
We use a custom `ConcurrentKafkaListenerContainerFactory` to enable two critical features:
*   **`isBatchListener = true`**: Switches the listener from receiving 1 record to receiving a `List<ConsumerRecord>`.
*   **`AckMode.MANUAL_IMMEDIATE`**: Prevents Kafka from automatically committing offsets. We take full control of the commit to ensure "Exactly-Once" processing.

### B. The "Wait-and-See" Retry Logic
Because the system is currently a "Split-Path" architecture (Projects are synchronous, Tasks are asynchronous), there is a risk that a Task event arrives before the Project DB transaction has finished.

*   **Logic**: If `insertTask` fails (returns null), the worker doesn't crash. It waits **100ms** and retries up to 3 times.
*   **Benefit**: This allows the synchronous Project transaction to "catch up" without requiring a complex distributed lock.

### C. Manual ACK & Backpressure
If the database becomes slow or goes down:
1.  The `TaskConsumer` transaction will fail.
2.  `ack.acknowledge()` will **not** be called.
3.  Kafka will not move the offset forward.
4.  Kafka naturally applies **Backpressure**—it stops sending new messages to this consumer until the current ones are processed, preventing the application from crashing due to memory overflow.

---

## 3. Optimistic Locking & Versioning
Every event (Update, Delete, Assign) includes the expected `version`. The `TaskQueries` implementation enforces this using a `WHERE version = ?` clause. If the version has changed in the DB since the event was produced, the update is ignored, maintaining data integrity during high-concurrency writes.

## 4. Summary of Components
- **`TaskConsumer.kt`**: The background worker processing the `workspace-activity` topic.
- **`KafkaConfiguration.kt`**: The infrastructure layer for batch and manual ACK support.
- **`ProjectTasksTable`**: Updated with `idempotencyKey` for final-layer deduplication.
