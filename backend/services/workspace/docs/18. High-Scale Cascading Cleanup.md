# 18. Universal Cascading Cleanup Strategy

In a system targeting **10k RPS**, synchronous cascading deletes (`ON DELETE CASCADE`) are dangerous. They create long-running transactions and lead to "Head-of-Line Blocking" in Kafka partitions.

Taskinator implements a **Universal Reactive Cascading Cleanup** strategy using **Independent Consumer Groups**.

## 1. The Cascade Matrix

| Trigger Action | Synchronous API Action | Emitted Domain Event | Async Cleanup Cascade (The "Drain") |
| :--- | :--- | :--- | :--- |
| **Delete Project** | Delete Project & Members | `ProjectDeleted` | 1. `TeamConsumer`: Purge Teams.<br>2. `TaskConsumer`: Purge Tasks. |
| **Remove Member** | Delete Project Members | `ProjectMembersRemoved` | 1. `TeamConsumer`: Remove Team Memberships.<br>2. `TaskConsumer`: Unassign Tasks. |
| **Delete Team** | Fetch Descendants -> Delete | `TeamDeleted` | 1. `TeamConsumer`: Purge sub-teams.<br>2. `TaskConsumer`: Unassign tasks for those teams. |
| **Delete Task** | Fetch Path -> Delete | `TaskDeleted` | 1. `TaskConsumer`: Purge sub-tasks. |

---

## 2. Distributed Consumption Model

Instead of a single orchestrator, we use **Independent Consumer Groups** listening to the same `workspace-activity` topic. 

1.  **ProjectConsumer** (`project-service-group`): Orchestrates high-level fan-out.
2.  **TeamConsumer** (`team-service-group`): Handles team-specific purges.
3.  **TaskConsumer** (`task-service-group`): Handles task-specific purges and unassignments.

### Benefits:
- **Parallelism:** Team cleanup and Task cleanup happen in parallel.
- **Isolation:** If the `TaskConsumer` is slow (deleting 1M tasks), it doesn't slow down the `TeamConsumer`.
- **Domain Autonomy:** Each domain package owns its event definitions and its worker logic.

---

## 3. Natural Ordering & Causal Consistency

We rely on Kafka's **Partition Key**. By using `projectId` as the key for ALL workspace events, Kafka guarantees that for any specific project:
- Events are delivered to exactly one partition.
- Events are delivered in the exact order they were produced.

This ensures that a "Delete Team" event is never processed *before* the "Create Team" event for that same project within any consumer group.
