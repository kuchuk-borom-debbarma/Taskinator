# 18. High-Scale Cascading Cleanup Strategy

In a system targeting **10k RPS**, synchronous cascading deletes (e.g., using `ON DELETE CASCADE` in SQL) are dangerous. They create long-running transactions, lock large portions of the database, and lead to "Head-of-Line Blocking" in Kafka partitions.

Taskinator implements a **Reactive Cascading Cleanup** strategy using a multi-level event fan-out. This ensures that a single project deletion doesn't block "live" mutations like task creations.

## 1. Architectural Principles
- **Asynchronous Deletion:** The API marks the project as "Deleted" and returns immediately.
- **Granular Fan-out:** Large delete operations are broken into smaller, domain-specific events.
- **Idempotency:** All cleanup consumers must be idempotent to allow for Kafka retries.
- **Resource Priority:** "Live" user traffic (Writes/Reads) should not be starved by background cleanup IO.

---

## 2. The Cleanup Cascade Flow

### Level 0: The Trigger (API/Ingest)
- **Event:** `ProjectEvent.ProjectDeleted(projectId)`
- **Action:** 
    - Mark `Projects.status = 'DELETED'` (Soft-delete/Status flag) to hide from UI immediately.
    - Emit `ProjectEvent.ProjectDeleted` to the `workspace-activity` topic.

### Level 1: Project-Level Consumers
The **Unified Consumer** receives `ProjectDeleted` and delegates to multiple specialized consumers/events:

| Consumer | Responsibility | Action |
| :--- | :--- | :--- |
| **Project Consumer** | Core Project Metadata | Deletes from `Projects` and `ProjectMembers`. |
| **Project Consumer** | Fan-out Trigger | Emits `CleanupEvent.TeamsRequested(projectId)`. |
| **Project Consumer** | Fan-out Trigger | Emits `CleanupEvent.TasksRequested(projectId)`. |

### Level 2: Entity-Level Consumers (The "Heavy Lifters")
These consumers process the granular cleanup events in parallel (often in different Kafka partitions or batches).

#### A. Team Cleanup (`CleanupEvent.TeamsRequested`)
The `TeamConsumer` performs a bulk deletion of all team-related structures for that project:
1. Delete from `ProjectTeamMembers` where `fk_project_id = projectId`.
2. Delete from `ProjectTeamClosure` where `fk_project_id = projectId`.
3. Delete from `ProjectTeams` where `fk_project_id = projectId`.

#### B. Task Cleanup (`CleanupEvent.TasksRequested`)
The `TaskConsumer` performs a high-performance bulk deletion:
1. Delete from `ProjectTasksTable` where `fk_project_id = projectId`.
2. *Note:* Because we use **Materialized Paths**, if we were deleting a single sub-tree, we would use `WHERE path LIKE 'root/parent/%'`. For a whole project, the `projectId` index is the most efficient.

## 3. Event Definitions & JSON Schema

### Project Level (`ProjectEvent`)
```kotlin
sealed class ProjectEvent {
    data class ProjectDeleted(val projectId: UUID) : ProjectEvent()
}
```

### Internal Cleanup Events (`CleanupEvent`)
These events are internal to the Workspace service and used to drive the parallel drain.

```kotlin
sealed class CleanupEvent {
    // Level 1 -> Level 2 Fan-out
    data class TeamsRequested(val projectId: UUID) : CleanupEvent()
    data class TasksRequested(val projectId: UUID) : CleanupEvent()
    
    // Level 2 -> Level 3 (If needed for external services)
    data class TaskAttachmentsCleanup(val taskIds: List<UUID>) : CleanupEvent()
}
```

## 4. Implementation Details (The "Drain" Phase)

### Batch Deletion for 100k+ Entities
If a project contains a massive number of tasks (e.g., 500,000), a single `DELETE FROM ... WHERE project_id = ...` might still time out or bloat the Transaction Log.

**The "Chunky Delete" Pattern:**
```kotlin
fun handleTaskCleanup(event: TasksRequested) {
    val limit = 5000
    do {
        val deletedCount = taskRepo.deleteBatch(event.projectId, limit)
        // If we hit the limit, we might want to re-emit the event 
        // to continue in the NEXT Kafka batch, keeping transactions short.
    } while (deletedCount == limit)
}
```

---

## 5. Failure Recovery & Consistency
- **Kafka Retries:** If a `TeamsRequested` consumer fails, Kafka will retry that specific event without re-running the `ProjectDeleted` logic.
- **Orphan Cleanup:** A nightly "Scavenger" job can look for any records where `fk_project_id` does not exist in the `Projects` table, cleaning up any orphans missed during partial failures.
