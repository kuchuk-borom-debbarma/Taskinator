# High-Scale Write Architecture (100k - 1M RPS)

At extreme scales (100k to 1M+ Writes Per Second), a standard relational database like PostgreSQL becomes the bottleneck. This document explains why, and how Taskinator scales using the **Ingest-Buffer-Drain** pattern.

## 1. The Problem: The "B-Tree" Wall
PostgreSQL uses **B-Trees** for indexing. When you insert a row:
1.  **WAL Write:** Sequential append to the Write-Ahead Log (Fast).
2.  **Index Update:** The DB must find the correct "leaf" in the B-Tree and update it (Random I/O).

At 1M RPS, the disk cannot physically perform enough random I/O operations to rebalance indices for every request. The CPU spends 90% of its time waiting for the disk head or the SSD controller to find the right memory address.

## 2. The Solution: Ingest-Buffer-Drain
We de-couple the **User Request** from the **Database Commit**.

### Phase A: Ingest (The API)
The API service does **zero** database writes.
1.  Receives the `POST /createTask` request.
2.  Performs basic validation (schema, auth).
3.  Pushes the "Intent" as a JSON event into a **Buffer** (Kafka or Redis).
4.  Returns `202 Accepted` immediately (Latency: < 5ms).

### Phase B: Buffer (The Safety Net)
This layer acts as a shock absorber for traffic spikes.
*   **Redis Cluster:** Stores data in RAM. Extremely low latency, but volatile if the cluster fails without persistence.
*   **Kafka:** Stores data as an **Append-Only Log** on disk. Slightly higher latency than RAM, but infinitely durable and handles "Backpressure" better.

### Phase C: Drain (The Worker)
A background consumer (Spring Boot `@KafkaListener` or Redis Worker) "drains" the buffer.
1.  **Micro-Batching:** Instead of processing 1 by 1, it fetches **5,000 events** at once.
2.  **JDBC Batching:** It executes a single `INSERT INTO ... VALUES (...), (...), ...` command.
3.  **Result:** Postgres only pays the "Transaction Cost" once for every 5,000 rows.

## 3. Redis vs. Kafka: Which one for Taskinator?

| Feature | Redis Cluster (Queue) | Kafka (Topics) |
| :--- | :--- | :--- |
| **Speed** | Sub-millisecond (Memory) | 2-10ms (Sequential Disk) |
| **Durability** | Risky (Lost on RAM failure) | Guaranteed (Persistence) |
| **Replayability** | Hard (Once read, it's gone) | Easy (Can re-read from "7 days ago") |
| **Scaling** | Horizontal (Cluster) | Horizontal (Partitions) |

**For Taskinator:** We prefer **Kafka**. While Redis is faster for pure "Volatile Writes" (like view counters), task data is critical. Kafka's ability to "Replay" events if the database goes down is essential for reliability.

## 4. Implementation Strategy (Kotlin/Spring)

Instead of a direct repository call in the controller, we move to a `Producer`:

```kotlin
// 1. API: Fast Ingest
@DgsMutation
fun createTask(@InputArgument input: CreateTaskInput): GenericResponse {
    // 1. Validate only
    // 2. Push to Kafka
    kafkaTemplate.send("task-ingest", input.projectId, input)
    
    return GenericResponse(success = true, message = "Queued for creation")
}

// 2. WORKER: Batch Persistence
@KafkaListener(topics = ["task-ingest"], batch = "true")
fun handleBatch(records: List<CreateTaskInput>) {
    transaction {
        // Exposed Batch Insert (Rewrites to 1 SQL call)
        ProjectTasksTable.batchInsert(records) { input ->
            this[title] = input.title
            // ... mapping
        }
    }
}
```

## 5. The Trade-off: Eventual Consistency
The only downside is that the data isn't in the database *the exact millisecond* the user gets a "Success" response.
*   **The User Experience:** The UI should optimistically show the new task, or the "Read Path" should check the **Redis Cache** (where the Ingest service also wrote the task) before falling back to the Postgres DB.
