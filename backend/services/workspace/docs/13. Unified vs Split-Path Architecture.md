# 13. Unified vs. Split-Path Architecture

This document explores the architectural trade-offs between our current **Split-Path** implementation and the long-term goal of a **Unified Entity Stream**. It details the risks of hybrid consistency and the strategy for ensuring causal ordering at scale.

## 1. Current State: The Hybrid Model
As of Phase 1, the Taskinator Workspace service operates on two distinct write paths:

| Feature | Path | Mechanism | Target Scale |
| :--- | :--- | :--- | :--- |
| **Tasks** | **Asynchronous (IBD)** | API → Kafka → Worker → DB | 1,000,000 RPS |
| **Projects & Teams** | **Synchronous** | API → Service → DB | 1,000 RPS |

---

## 2. The "Split-Path" Risk: Causal Race Conditions
The biggest danger in a hybrid model is the loss of **Causal Ordering**. If User A creates a Project and then immediately creates a Task within that project, the system faces a "Race to the Database."

### The Failure Sequence:
1.  **API (Sync Path)**: Starts `INSERT INTO projects`. (Transaction is open but not yet committed).
2.  **API (Async Path)**: Receives "Create Task," generates ID, and pushes to Kafka.
3.  **Worker (Drain)**: Pulls the task from Kafka and attempts `INSERT INTO tasks`.
4.  **Database Error**: The `tasks` insert fails with a `Foreign Key Violation` because the `Project` transaction in Step 1 hasn't finished yet.

### Result: "Ghost Failures"
The Task worker will either crash, send the task to the Dead Letter Queue (DLQ), or require complex "Retry-with-Exponential-Backoff" logic to wait for the Project to appear in the database.

---

## 3. The Solution: The Unified Entity Stream
To eliminate race conditions, we must move toward a **Unified Entity Stream** where every mutation for a specific workspace travels through the same Kafka pipe.

### How it works:
- **Topic**: `workspace-activity`
- **Partition Key**: `projectId`
- **The Stream**:
    - `[Offset 101]: ProjectCreated`
    - `[Offset 102]: TeamCreated`
    - `[Offset 103]: TaskCreated`

### Why this is "Perfect" Consistency:
Because Kafka guarantees that a single consumer thread will process Partition X in order, the worker will **never** see a task before it has successfully processed and committed the project it belongs to.

---

## 4. Implementation Strategy: The "Staging" ID
To make Projects and Teams asynchronous, we solve the "Unknown ID" problem using **API-Side Identity**:

1.  **Request**: `POST /createProject(name: "New Project")`
2.  **API Generation**: API generates `projectId = UUID-V7-XYZ`.
3.  **Kafka Write**: API pushes `ProjectCreated(id: UUID-V7-XYZ)` to Kafka.
4.  **Response**: API returns `202 Accepted { id: UUID-V7-XYZ }`.
5.  **Subsequent Tasks**: The client uses `UUID-V7-XYZ` for all tasks, which also land in the same Kafka partition.

---

## 5. Short-Term Mitigation (The "Wait-and-See" Worker)
Until we migrate Projects and Teams to Kafka, our **Task Worker** must be defensive. Instead of failing immediately on a missing Project, the worker should:
1.  Catch the Foreign Key error.
2.  Sleep for **50ms - 100ms**.
3.  Retry the insert.
4.  If it fails after 3 retries, only then move it to the **DLQ**.

## 6. Conclusion
The current hybrid model is a necessary stepping stone to prove the 1M RPS task ingest logic. However, to achieve a truly robust, race-condition-free system, the **Unified Entity Stream** is the final destination.

**Status**: 
- Tasks: **Asynchronous (Done)**
- Projects/Teams: **Synchronous (Pending Migration)**
