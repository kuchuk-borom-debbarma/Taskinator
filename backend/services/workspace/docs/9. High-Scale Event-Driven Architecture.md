# 9. High-Scale Event-Driven Architecture (Low-Level Design)

This document details the technical implementation of the **Ingest-Buffer-Drain** pattern designed to handle 100k to 1M Writes Per Second (RPS) within the Taskinator Workspace service.

## 1. The Core Lifecycle
To bypass the "B-Tree Wall" of relational databases, we decouple the user request from the database transaction.

1.  **Ingest:** API validates, generates IDs, and buffers the intent in Kafka.
2.  **Buffer:** Kafka ensures durability and causal ordering.
3.  **Drain:** Worker pulls large batches (5,000+) and performs a single JDBC batch insert into PostgreSQL.

---

## 2. The Ingest Layer (API Service)
The API must be non-blocking and extremely lightweight.

*   **ID Generation:** We use **UUID v7** (time-ordered). The API generates the ID before the event is sent.
*   **Validation:** Basic schema and auth checks only. Complex business logic is deferred to the Worker.
*   **Response:** Returns `202 Accepted` + the generated ID.

---

## 3. The Buffer Layer (Kafka Topology)
We use a **Unified Entity Stream** to guarantee causal ordering (e.g., Project must exist before Task).

### Topic: `workspace-activity`
*   **Partitions:** 256 (calculated for 1M RPS / 4k batch-write capacity per worker).
*   **Replication Factor:** 3 (Min In-Sync Replicas: 2).
*   **Partition Key:** `projectId` (UUID).
    *   *Why:* Ensures all events for the same project land in the same partition and are processed sequentially.

### Producer Configuration (API)
| Property | Value | Rationale |
| :--- | :--- | :--- |
| `acks` | `all` | Zero data loss. |
| `compression.type` | `lz4` | Optimal CPU/Compression ratio for high RPS. |
| `batch.size` | `131072` (128KB) | Reduces network syscalls. |
| `linger.ms` | `5` | Wait for batch to fill. |
| `enable.idempotence`| `true` | Prevents duplicates on network retry. |

---

## 4. The Drain Layer (The Batch Worker)
The worker uses **Double Batching** to maximize throughput.

### Step 1: Kafka Poll Batch
The worker fetches up to 5,000 records in one network trip.
*   `max.poll.records: 5000`
*   `fetch.min.bytes: 1048576` (1MB)

### Step 2: JDBC Rewrite Batch
The worker groups the records by type and executes a multi-row INSERT.
*   **JDBC URL:** `jdbc:postgresql://.../db?reWriteBatchedInserts=true`
*   **SQL generated:** `INSERT INTO tasks (id, title, ...) VALUES (?,?,...), (?,?,...), ... (x5000)`

### Error Handling: The DLQ
If a batch fails (e.g., a "Poison Pill" event):
1.  The worker catches the exception.
2.  The batch is sent to a `workspace-activity-dlq`.
3.  The Kafka offset is committed to move past the error.

---

## 5. Idempotency & Exactly-Once Semantics
In a distributed system handling 1M RPS, duplication is inevitable. We handle this using **Idempotency Keys**.

### At the Producer (API)
- Every "Write" intent is assigned a unique `idempotencyKey` before being sent to Kafka.
- Kafka uses these keys to discard duplicate messages at the broker level.

### At the Consumer (Worker)
- The database acts as the final shield using **UNIQUE** constraints on the `idempotency_key` column.
- The worker uses an "INSERT IGNORE" strategy: `ON CONFLICT (idempotency_key) DO NOTHING`.

---

## 6. Read Consistency: Lazy Database-First
Unlike systems that require immediate visibility of "In-Flight" data, Taskinator prioritizes **Database-as-Truth**.

1.  **Request**: `GET /tasks?projectId=123`
2.  **Read Source**: The API queries **PostgreSQL** directly.
3.  **Result**: The user only sees data that has been successfully "Drained" from Kafka and committed to the DB.
4.  **Lazy Caching (L1)**: Once data is read from the DB, it is cached in **Redis** with a short TTL to speed up subsequent identical requests.
5.  **UX Strategy**: The Frontend should use **Optimistic UI** (local state updates) to handle the 100ms-500ms lag while Kafka is being processed.

---

## 7. Future Solution: Hot Partition Mitigation
If a single "Super Project" generates >10k RPS, it will overwhelm its assigned partition.

*   **Key Salting:** If a project hits a threshold, the producer appends a salt: `projectId + "_" + random(1..8)`.
*   **Dedicated Topics:** Move known high-traffic projects to a dedicated topic.
*   **Postgres Partitioning:** Use declarative table partitioning in the DB to avoid B-Tree contention.

---

## 8. Infrastructure Requirements
*   **Kafka:** 9 Brokers, NVMe SSDs, 10Gbps Network.
*   **Redis:** Cluster mode, `volatile-lru` eviction policy.
*   **Postgres:** `synchronous_commit = off` (for Worker connections) to increase commit throughput.
