# 11. Federated N+1 Resolution (Gateway & Subgraph Handshake)

In a Federated architecture, solving the N+1 problem requires a coordinated effort between the **Apollo Gateway (Network level)** and the **Subgraph DataLoaders (Database level)**. This document details the "Handshake" that ensures high-performance data fetching across service boundaries.

## 1. The Two-Tier Batching Model

To fetch 100 tasks and their owners' names, the system avoids $100+100$ queries through a tiered approach:

| Tier | Component | Responsibility | Prevents |
| :--- | :--- | :--- | :--- |
| **Tier 1** | **Apollo Gateway** | Cross-service "Network" Batching | 100 HTTP calls to Identity Service |
| **Tier 2** | **Subgraph DataLoader** | Local "Database" Batching | 100 SQL calls to Identity PostgreSQL |

---

## 2. Tier 1: The Gateway "Query Plan"
When the Gateway receives a query spanning multiple services, it generates a **Query Plan**.

### The Entity Collection (Intelligence)
1.  **Initial Fetch:** The Gateway fetches the requested tasks from the `Workspace Service`.
2.  **Deduplication:** It extracts all `ownerId` values from the task list and creates a unique set.
3.  **The `_entities` Request:** The Gateway automatically constructs a batch request to the `Identity Service` using the specialized `_entities` field.

```graphql
# Gateway-generated batch request
query($representations: [_Any!]!) {
  _entities(representations: $representations) {
    ... on User {
      name
      avatarUrl
    }
  }
}
```

**The `representations` variable:**
```json
{
  "representations": [
    { "__typename": "User", "id": "uuid-1" },
    { "__typename": "User", "id": "uuid-2" }
  ]
}
```

---

## 3. Tier 2: The Subgraph DataLoader (Identity Service)
Inside the `Identity Service` (Hono/Drizzle), the `_entities` resolver is triggered. Without a DataLoader, this resolver would still perform one DB query per ID in the `representations` list.

### The Handshake Mechanics
1.  **Context Injection:** The `Identity Service` extracts the `X-User-Id` header (propagated by the Gateway) into its local request context.
2.  **Batch Loading:** The `_entities` resolver passes all 100 IDs into a `UserDataLoader`.
3.  **Drizzle/SQL Batch:** The DataLoader executes a single optimized query:
    ```sql
    SELECT id, name, avatar_url 
    FROM users 
    WHERE id IN ('uuid-1', 'uuid-2', ...)
    AND (is_public = true OR id = $requesting_user_id);
    ```

---

## 4. Extending Entities (Workspace Service)
When the "Read Path" requires Workspace data for a list of Users (e.g., `User.tasks`), the roles are reversed:

1.  **Identity Service** returns the basic User profiles.
2.  **Gateway** collects the User IDs and sends a batch request to the **Workspace Service**.
3.  **Workspace DataLoader** receives the batch of User IDs.
4.  **SQL Batch:** It fetches all tasks where `owner_id IN (...)` and the `requesting_user_id` has permission to view the parent project.

---

## 5. Critical Configuration: Header Propagation
For this "Handshake" to be secure, the Gateway must be configured to propagate identity headers to all subgraphs.

**Gateway/Router Config (yaml):**
```yaml
headers:
  all:
    forward:
      - name: "X-User-Id"
```

This ensures that every DataLoader, regardless of which service it lives in, knows **who** is asking for the data and can apply row-level security filters during the batch SQL execution.

## 6. Summary of Benefits
*   **Latency:** Replaces $O(N)$ network latency with $O(1)$ batch latency.
*   **Database Health:** Replaces high-overhead random I/O (many small queries) with efficient sequential scans (one large query).
*   **Encapsulation:** Subgraphs don't need to know about each other; they only need to know how to resolve their own "Entities" in batch when asked by the Gateway.
